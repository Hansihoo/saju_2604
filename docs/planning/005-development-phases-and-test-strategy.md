# Development Phases And Test Strategy 005

## 목적
- MVP를 실제 구현 가능한 작은 개발 회차로 나눈다.
- 각 회차마다 무엇을 만들고 무엇을 검증해야 하는지 기준을 세운다.
- 나중에 개발이 길어져도 순서가 흔들리지 않게 한다.

## 개발 기본 원칙
- 한 회차에는 하나의 작은 사용자 가치 또는 하나의 작은 기술 목표만 넣는다.
- 시간 보정과 계산 정확도는 UI보다 우선 검증한다.
- LLM은 마지막 표현 레이어이므로, 계산/분석 엔진이 먼저 신뢰 가능한 상태가 되어야 한다.
- `출생시간 미상 -> 00:00 입력`은 허용하지만, 시주 기반 결과 제한 규칙을 먼저 코드와 테스트에 반영해야 한다.

## 전체 구현 순서
1. 입력/응답 계약 확정
2. 지역 검색과 입력 검증 구현
3. 시간 보정 모듈 구현
4. 양력/음력 정규화와 사주 계산 어댑터 구현
5. 분석 엔진 구현
6. LLM 표현 레이어 구현
7. 결과 화면과 상세 근거 UX 구현
8. CI, 로그, 헬스체크, 회귀 테스트 정리

## 권장 개발 회차

### 회차 1. 계약과 더미 파이프라인
- 목표:
  - 프런트와 백엔드가 같은 입력/응답 스키마를 공유할 수 있게 한다.
- 구현:
  - 입력 스키마 정의
  - 결과 응답 스키마 정의
  - `is_birth_time_estimated`, `hour_pillar_enabled` 같은 가드 필드 정의
  - 더미 응답으로 전체 요청/응답 흐름 연결
- 완료 기준:
  - 입력 화면에서 요청을 보내면 결과 화면이 더미 데이터로 렌더링된다.
  - 출생시간 미상 플래그가 응답 구조에 포함된다.
- 테스트:
  - API 스키마 unit test
  - 프런트 폼 validation test
  - API smoke test

### 회차 2. 지역 검색과 입력 UX
- 목표:
  - 지역을 자유 텍스트가 아닌 선택 가능한 정규화 데이터로 받는다.
- 구현:
  - 한국 지역 데이터셋 준비
  - 검색어 기반 후보 리스트 API
  - 프런트 자동완성 입력 UI
  - 지역 선택 전 제출 방지
- 완료 기준:
  - 사용자가 텍스트를 입력하면 후보 리스트가 나온다.
  - 후보를 선택해야 제출 가능하다.
- 테스트:
  - 지역 검색 unit test
  - 자동완성 UI component test
  - E2E: 지역 입력 -> 후보 선택 -> 제출 가능 확인

### 회차 3. 시간 보정 모듈
- 목표:
  - IANA 타임존, 역사적 시간 변경, DST를 포함한 보정 결과를 만든다.
- 구현:
  - `country/city -> iana_timezone` 매핑
  - 로컬 입력 시간 -> 보정 시간 계산
  - 시간 보정 메타데이터 반환
  - 시간 보정 실패 시 사용자 메시지 규칙 정의
- 완료 기준:
  - 입력된 지역과 시각에 대해 보정 시각과 근거를 얻을 수 있다.
  - 실패하면 계산 파이프라인이 중단되고 에러 응답이 나온다.
- 테스트:
  - unit: 타임존 변환
  - unit: DST 케이스
  - integration: 지역 선택 -> 보정 시각 계산
  - golden test: 사전에 정한 한국 케이스 비교

### 회차 4. 양력/음력 정규화 + 사주 계산 어댑터
- 목표:
  - 입력값을 계산 엔진이 받는 정규화 포맷으로 바꾸고, FortuneFlow 계산 코어를 연결한다.
- 구현:
  - 양력/음력 변환 계층
  - `corrected_solar_date` 생성
  - FortuneFlow 어댑터 레이어 작성
  - 사주팔자/만세력 기본 결과 추출
- 완료 기준:
  - 양력/음력 어느 쪽 입력이어도 동일한 내부 계산 포맷으로 정규화된다.
  - 계산 결과에서 사주팔자와 기본 만세력 구조를 얻을 수 있다.
- 테스트:
  - unit: 양력/음력 변환
  - integration: 보정 시간 -> 계산 결과
  - golden test: 알려진 샘플 케이스 비교
  - regression test: FortuneFlow 결과와 핵심 값 비교

### 회차 5. 시주 비활성화 규칙
- 목표:
  - 출생시간 미상일 때 잘못된 과신을 막는 가드레일을 구현한다.
- 구현:
  - `00:00` + 추정 플래그 처리
  - 시주 기반 데이터 노출 제한 규칙
  - 시주 기반 점수/등급 제외 또는 별도 처리
  - 제한 안내 메시지 정의
- 완료 기준:
  - 추정 시간 입력 시 시주 기반 섹션이 비활성화된다.
  - 계산 결과가 일반 결과처럼 오해되지 않는다.
- 테스트:
  - unit: 가드 규칙 테스트
  - integration: 추정 시간 케이스 응답 구조 확인
  - E2E: 시간 미상 사용자 흐름

### 회차 6. 분석 엔진
- 목표:
  - 코드 기반 점수/등급 산출과 해석 근거 생성 규칙을 만든다.
- 구현:
  - 오행 분포 분석
  - 십성 분석
  - 대운 구조 정리
  - 점수 계산
  - 등급 계산
  - 사용자용 근거 요약 생성
- 완료 기준:
  - 동일 입력에 대해 항상 같은 점수/등급이 나온다.
  - 등급 산출 근거를 코드 레벨에서 설명할 수 있다.
- 테스트:
  - unit: 점수 함수
  - unit: 등급 경계값
  - property test 또는 테이블 테스트: 규칙 일관성
  - snapshot: 분석 결과 구조

### 회차 7. LLM 표현 레이어
- 목표:
  - 계산/분석 결과를 사용자 친화적 결과 문장으로 만든다.
- 구현:
  - LLM 입력 프롬프트 구조
  - 출력 JSON 스키마
  - 안전장치와 후처리
  - 비활성화 섹션 반영
- 완료 기준:
  - LLM이 판단을 새로 만들지 않고 입력 데이터에 맞는 표현만 생성한다.
  - 필수 섹션 누락 시 재시도 또는 fallback이 작동한다.
- 테스트:
  - unit: prompt builder
  - contract test: 출력 스키마 파싱
  - integration: mock LLM / real provider 분리 테스트

### 회차 8. 결과 화면
- 목표:
  - 요약형 결과와 상세 근거 UX를 완성한다.
- 구현:
  - 요약 카드
  - 강점/약점/운세 섹션
  - 오행/십성/대운 접힘 패널
  - 시주 제한 안내 UI
- 완료 기준:
  - 사용자는 요약만 보고도 결과를 이해할 수 있다.
  - 원하면 근거를 펼쳐볼 수 있다.
- 테스트:
  - component test
  - E2E: 정상 조회 / 시간 미상 / 지역 선택 실패
  - 시각 회귀 또는 스냅샷 테스트

### 회차 9. 운영 준비
- 목표:
  - CI와 배포 전 검증 루틴을 만든다.
- 구현:
  - lint/test/typecheck/build 명령 정리
  - CI workflow
  - API healthcheck
  - 기본 로그 포인트 정리
- 완료 기준:
  - PR에서 필수 검증이 자동으로 돈다.
  - 배포 후 헬스체크와 주요 흐름 확인이 가능하다.
- 테스트:
  - CI dry-run 수준 검증
  - API health smoke test
  - 수동 배포 체크리스트

## 테스트 계층 전략

### 1. Unit Test
- 목적:
  - 계산과 규칙을 가장 빠르게 검증한다.
- 대상:
  - 시간 보정 함수
  - 양력/음력 변환
  - 지역 검색 매핑
  - 시주 비활성화 규칙
  - 점수/등급 계산

### 2. Integration Test
- 목적:
  - 모듈 사이 연결이 맞는지 확인한다.
- 대상:
  - 입력 -> 시간 보정
  - 시간 보정 -> 사주 계산
  - 계산 -> 분석 엔진
  - 분석 -> LLM formatter
  - API 엔드포인트 end-to-end without browser

### 3. Golden Test
- 목적:
  - 알려진 입력 케이스에 대해 계산 결과가 흔들리지 않는지 확인한다.
- 대상:
  - 한국 표준 지역 케이스
  - 절기 경계 케이스
  - 자시/야자시 경계 케이스
  - 양력/음력 동일 인물 변환 케이스

### 4. E2E Test
- 목적:
  - 사용자 흐름이 실제로 동작하는지 확인한다.
- 대상:
  - 정상 입력 -> 결과 조회
  - 지역 자동완성 선택
  - 출생시간 미상 흐름
  - 시간 보정 실패 메시지
  - 결과 상세 펼침

### 5. Manual Verification
- 목적:
  - 문장 톤, UI 이해도, 제한 안내 문구를 사람 눈으로 확인한다.
- 대상:
  - 결과 문장 자연스러움
  - 과장 표현 여부
  - 시주 제한 안내 가독성

## 반드시 먼저 만들 테스트
- 시간 보정 golden test
- 양력/음력 정규화 test
- 출생시간 미상 가드 test
- 지역 선택 integration test

## 회차별 기본 검증 명령 초안
- 프런트:
  - `pnpm test`
  - `pnpm lint`
  - `pnpm typecheck`
  - `pnpm build`
- 백엔드:
  - `pytest`
  - `ruff check`
  - `mypy`
- E2E:
  - `playwright test`

## 이번 회차 결정
- 구현은 계산 정확도와 계약 안정성을 먼저 만든 뒤 UI를 확장한다.
- 테스트는 unit -> integration -> golden -> e2e 순으로 쌓는다.
- 출생시간 미상과 시간 보정은 일반 화면 개발보다 먼저 검증 기준을 세운다.
