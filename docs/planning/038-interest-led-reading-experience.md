## 2026-10-09 풀이 목차와 작성 체계

사용자는 다른 서비스의 풀이/흥미 장치를 참고해 이후 작성이 따를 목차를 요청했다. 제품 JSON의 독립 `reading_outline_design` (`fortune-reading-outline-2026-10-09.1`)에 보존한다. **목차 제안과 작성 기준의 문서화**이며 현재 결과·질문 목록·규칙·프롬프트를 바꾼 것은 아니다. 기존048의 다섯 분류 ID와 순서는 유지한다.

목표는 개인별 복과 불리함, 시기별 변화를 먼저 읽고 각 분야에서 더 알고 싶은 질문으로 이어지는 경험이다. 영향 범위는 기획/작성 문서와 독립 제품 계획 메타데이터다. 주요 위험은 제목만 미래형으로 바꾸기, 타고난 복을 성격 장점으로 대체하기, 빈 지식으로 기간/강도를 채우기다. 검증은 JSON/순서/연결 일치와 기존 helper 및 fallback-only 사용자 시나리오이며 새로운 문장의 효용·명리 정확도 검증과 구별한다.

위 질문은 **목표 답변의 예시**다. 현재 서버 지원 질문 목록을 승격하는 지시가 아니다. 만남/취업 시기와 분야별 종합 길흉·강도·기간 우열 규칙은 여전히 미구현 또는 검토 대상이다. 재성·관성·신살의 존재, 개수, 편집 비중만으로 이를 채우지 않는다. 실제 사건 확률·인구 순위·평생의 불행을 만들지 않으며 critical/시간 미상 제한은 유지한다.

### 각 장의 작성 순서

1. 개인별 **한 줄 결론**을 먼저 쓴다. ‘무엇을 살펴볼게’ 같은 예고문이나 전문 분류명만으로 끝내지 않는다.
2. 그 결론이 사용자에게 뜻하는 복·기회·불리함과 필요한 조건을 충분히 설명한다. 긍정/부정을 억지로 하나씩 채우거나 모든 부담을 장점으로 미화하지 않는다.
3. 지원되는 경우 현재와 이후 기간을 비교한다. 관련 분야의 변화를 여기서 읽고, 마지막 장은 전체 흐름과 전환을 묶는다.
4. 실제 지원하는 관련 질문만2~3개 이하로 둔다. 본문의 핵심 질문을 그대로 되묻기보다 시기·조건·세부 비교로 깊어진다. 본문에 답이 없고 질문만 있는 화면을 만들지 않는다. 상황 확인이 필요한 선택 질문만 추가 입력을 받으며 솔로/구직 등을 추측하지 않는다.
5. 용어·위치·규칙·관법 차이는 작은 기본 접힘 **풀이 메모**에 둔다. 본문 주장의 중요한 조건과 계산 불확실성은 밖에 남긴다.

이는 기존의 고정 `scene/tradeoff/action` 세 문단을 새 고정 다섯 문단으로 대체하는 계약이 아니다. 정보에 맞춰 분량을 조정하고 일반 조언·행동 숙제로 채우지 않는다. 친근한 반말과 짧은 비유로 결론을 전달하되 시비/조롱/무조건 긍정/정확도 홍보는 하지 않는다.

도화·귀인·역마 등은 실제 확인됐을 때 관련 장에 설명하고, 없으면 빈 전용 장이나 ‘없다’는 자동 언급을 만들지 않는다. 발견 자체를 개인별 길흉 판정으로 확대하지 않는다. 오늘의 운세는 별도 짧은 재방문 콘텐츠, 공유는 검토된 본문 한 문장과 표정으로 둔다. 지수/공유/일일 콘텐츠를 장으로 늘려 주 풀이를 분산하지 않는다.

결과 첫 화면은 짧은 직접 답과 지원된 기간/변화를 읽는다. 기존 기본 결과 주제인 오늘과 단일 진입은 유지하며, 새 질문별 추천은 판정 지원 후 결과 내부에 연결하는 방향이다. 지수는039의 별도 설계에 따른 보조 정보이며 규칙/척도 검토 전 임의 숫자로 채우지 않는다. 숫자를 실제 성공 확률 또는 남들과의 운 순위로 제시하지 않는다.

이어지는 본문은 실제 관련 사실이 있는 만큼 충분히 설명한다. 편집 검토용 주제당 대략500~900자에서 시작해 정보에 맞춰 조정할 수 있으나 길이를 통과 기준으로 삼지 않는다. 주목한 기간의 비교, 내 명식의 여러 단서, 유리한 해석과 반대 단서, 맥락에 맞는 행동을 구별한다. 같은 scene/tradeoff/action 세 문단에 내용을 억지로 줄이지 않는다. **현재 런타임의 고정 형식은 변경하지 않았으며**, 새 형식 도입은 사실/규칙/문구 계약과 호환 검증을 별도 버전으로 진행해야 한다. 중요 지원 한계는 주장과 함께 읽히며 전문 용어/세부 계산은 작은 기본 접힘 풀이 메모에 둔다.

흥미 장치는 검증할 가설이다. 우선순위는 기간의 차이, 실제 여러 단서에서 나오는 개인별 내용, 상황에 맞는 답이다. 도깨비는 짧고 친근한 반응과 표정으로 의미를 전달하며 시비·조롱·임의의 정확도 홍보를 하지 않는다. 요약은 정해진 결론을 쉬운 말로 쓰고, 내용에 없는 사건/날짜를 호기심 문구로 추가하지 않는다. 긴 풀이 중 지원된 한 문장을 골라 기존 공유 카드에 담는 방향을 유지한다. 주제/기간이 필요한 경우 표시하고 출생정보·전체 명식·메모는 기본 공유에 포함하지 않는다. 공유된 한 문장을 수신자가 다른 사람의 운과 비교하는 순위로 만들지 않는다.

재방문은 오늘/대상 기간의 실제 사실이나 판정이 달라졌을 때 새 내용을 제공하는 방향이다. 문장만 매번 바꾸거나 근거 없는 마감/행운 카운트다운·미지원 질문·인위적 잠금으로 유도하지 않는다. 첫 진입은 지금의 운세 보기 한 개 CTA와 주제 안내를 유지한다. 연애/직장 상황은 결과 안에서 선택·변경하는042의 설계와 연결한다.

공개 기능과 흥미 가설은 구별한다. 2026-10-08 다시 확인한 [포스텔러 개발사 앱 설명](https://play.google.com/store/apps/details?hl=ko&id=com.un7qi3.forceteller)은 주제별 풀이·월운·날짜별 점수를 소개하고, [공식 서비스 소개](https://un7qi3.co/ko/service)는 주제별 캐릭터를 설명한다. 이는 형식 사례이며 효과나 예측 정확도의 검증이 아니다. 우리 적용은 위의 사용자 피드백과 실제 지원 범위를 기준으로 판단한다.

내용 검토는 선택 질문에 답했는지, 같은 사람의 기간을 비교했는지, 같은 생일/조건에서 결과가 재현되는지, 여러 관련 사실을 연결했는지, 상황과 맞는지, 필요한 한계를 숨기지 않았는지 먼저 확인한다. 실제 흥미는 독자가 새 정보를 얻었는지, 한 문장을 기억하는지, 공유/다음 질문/재방문을 원하는지 별도 사용자 평가로 확인한다. 기존 구조 검사만으로 흥미 통과를 보고하지 않는다.

우선 보강은 새 인연과 구직의 시기 답변이다. 각각 답 명세·기간 사실·검토된 규칙·지원 조건을 갖춘 뒤 본문/메모/공유를 연결한다. 지수·문장 선택 공유·다른 상황은 관련 상태 표에 따라 후속으로 진행한다. 이 회차는 정보/흥미 설계 문서화이며 코드/UI/provider/배포 또는 실제 모델 호출 변경은 없다.

## 2026-10-08 기본 사주 후 질문 선택 흐름

후속 구현은 [043](043-basic-question-reading.md)에서 관리한다. 기본 명식 → 지원되는 계산 사실 질문 네 가지 → 선택한 답/메모/공유를 연결했다. 아래 문단은 당시 설계 판단의 기록이며, 현재 UI의 기본 결과는 today가 아니라 basic_chart다. 사건 시기·연애 상황·지수 기능의 별도 미지원 상태는 그대로다.

사용자는 기본 사주를 먼저 읽고 질문 목록에서 선택한 뒤 그 질문에 맞는 풀이를 받는 방향을 제안했다. **구현 가능한 후속 흐름**이며 `information_design.question_reading_flow`에 기록했다. 현재 runtime의 한 개 진입 CTA와 today 기본 결과는 변경하지 않았다. 구현 시 첫 결과를 기본 사주로 바꾸고 질문별 결과를 추가한다. 첫 진입에서 모든 운세 중 하나를 고르게 하는 기존 문제를 복원하지 않는다.

1. 기존 `운세 보기`와 출생 입력을 사용한다.
2. 서버가 계산한 팔자·일간·계절·겉/지장간·신살의 종류/위치·확인된 대운 기간을 쉬운 사실 요약과 함께 먼저 표시한다. 중요 계산 한계는 함께 표시하고 성격/타입 질문을 첫 진입 훅으로 사용하지 않는다.
3. 서버가 현재 입력/규칙으로 지원하는 질문을 제공한다. 처음에는3~5개를 편집해 제시하고 지원 질문이 더 있으면 주제별로 확장한다. 개수 목표를 맞추려고 미지원 시기/확률/상대 속마음 질문을 공개하지 않는다.
4. 질문에 필요한 상황만 추가로 확인한다. 연애는 새 인연/교제 중, 직장은 구직/재직처럼 입력 목적을 구별하며 미응답을 임의 추정하지 않는다.
5. 질문별 판정과 문장화로 직접 답·기간 비교·개인별 이유·해석 한계·행동·작은 메모를 제공한다. 질문을 바꾸면 같은 topic 본문을 제목만 바꿔 재사용하지 않는다.
6. 같은 기본 사주에서 다음 지원 질문으로 이동하거나 허용 문장을 공유한다. 출생정보를 다시 입력시키지 않는다.

확인된 재사용 지점: `create_saju_preview_response(report_mode="none")`는 문장 생성 없이 계산/분석을 준비한다. `prepare_detail_analysis_bundle`도 이를 호출하며 `render_detail_insight`와 준비/생성의 TTL/LRU cache가 이미 분리돼 있다. 현재 상세 유형은 `love_timing`, `wealth_timing`, `career_timing` 세 가지다. 이름이나 휴리스틱 기간 bundle을 새 만남/취업 질문의 검토된 지원으로 간주하지 않는다. `SajuPreviewRequest`는 question ID와 상황 필드가 없으므로 신규 선택 계약이 필요하다.

질문별 계약은 `question_id`, 필요한 context, 대상 기간, 사실/규칙/문구/형식 버전을 포함한 별도 추가 경로로 설계한다. 기존 API와 topic 카드/카탈로그의 엄격한 선택 조건을 보존한다. backend가 필요한 사실·검토된 규칙·허용 claim을 고르고 모델은 정해진 범위를 문장화한다. frontend가 생년월일에서 시기나 운의 유리함을 판단하지 않는다. 질문 목록의 title 변경도 실제 답변 범위 변경과 구별한다.

서버가 검증한 입력/계산을 재사용하며 client가 전달한 snapshot을 계산 사실로 신뢰하지 않는다. 입력 hash는 일치 확인용이며 권한 확인으로 사용하지 않는다. 캐시는 질문/상황/대상 기간/locale/관련 버전/모델 조건을 구별하고 mutable payload 공유를 피한다. 입력 변경·캐시 만료·서버 재시작 시 보유한 원본 입력으로 재준비한다. 새 영구 출생정보 저장이나 URL 노출은 기본 도입하지 않는다.

처음부터 모든 질문의 긴 풀이를 생성하지 않고 선택한 질문만 생성한다. 반복 질문의 검증된 캐시를 사용하며 중복 클릭/실패 후 자동 재생성/지난 답 덮어쓰기를 막는다. 기본 사실의 조기 표시는 모델 생성 대기를 앞부분에서 줄이는 목표지만 실제 속도/비용 감소를 측정한 것은 아니다. 여러 질문을 읽으면 추가 생성량이 늘 수 있으므로 모델 호출/예산/캐시를 함께 검토한다. 기존 실제 진행 표시를 재사용할 경우 질문 경로의 실제 단계에 맞는 별도 이벤트 계약이 필요하다.

후속 검증은 질문 A/B의 판정 차이, 상황 변경, 같은 질문 반복 캐시, locale/기간/버전 변경, 입력 변경과 stale 응답, 취소/중복, 지원 질문만 공개, 한계/메모/공유 의미 일치를 포함한다. 실제 기본 사주→질문→답→다음 질문 흐름과 모델 속도/질문 만족은 구현 후 확인한다. 이번에는 소스 확인과 설계 문서화만 했고 endpoint/UI/cache/model 호출을 바꾸지 않았다.

## 목표와 범위

사용자 결정: 서비스의 수익화는 현재 목표에서 제외하고 흥미에 집중한다. 사용자가 원하는 핵심은 **인연은 언제 들어오는지, 일과 대우의 흐름은 언제 달라지는지, 지금 움직여도 되는지**와 같은 앞으로의 일과 시기에 대한 답이다. 성격·연애 타입·편한 환경을 설명하는 질문을 첫 관심사로 삼지 않는다.

초안의 “내가 편한 연애는 어떤 모습일까?”, “내 강점은 언제 부담으로 바뀔까?”를 주력 진입 질문으로 제안한 방향은 폐기한다. 현재 엔진이 답하기 편한 성향 질문으로 사용자 의도를 대체한 것이 문제였다. 새 순서는 **원하는 답 정의 → 필요한 기간 계산·해석 규칙 확보 → 질문 공개 → 읽기와 공유**다.

결제·광고·유료 잠금·상담 판매·현금성 보상·플랫폼 입점은 이번 보강 범위에 포함하지 않는다. 결과를 보기 위한 추가 설문이나 계정 흐름도 도입하지 않는다. 이는 서비스 수익화에 관한 제품 결정이며, 기존 생성 provider 설정을 바꾼다는 뜻은 아니다.

경쟁 서비스에서 관찰한 콘텐츠 편집, 캐릭터 대화, 쉬운 접근을 우리 규모에 맞게 적용한다. 공개 자료와 가설의 구별은 [경쟁 서비스 조사](../ai/COMPETITOR_GROWTH_RESEARCH.md)를 따른다. 경쟁사의 화면·문구·캐릭터를 복제하지 않는다.

## 사용자 시나리오

### 처음 온 사용자

1. 도깨비와 “사주에 있는 그대로 말해줄게.”, `운세 보기` 버튼 및 아래의 제공 운세 안내를 본다. 이후 미래 질문이 준비되면 ready인 질문만 공개한다.
2. `운세 보기`를 누른다. 현재 입력에는 선택 주제를 표시하지 않는다. 향후 질문별 요청/결과가 실제 구현되면 지원 질문의 진입을 별도로 설계한다.
3. 기존 2단계 입력으로 생년월일·성별·태어난 시간·출생지를 입력한다. 시간 미상도 가능하다.
4. 오늘의 운세부터 읽고 받은 결과 안에서 원하는 주제로 이동한다. 미래 질문이 지원되면 현재 흐름·주목할 기간·그 기간의 근거를 제시한다. 본문·장면·행동은 바로 표시하고 작은 풀이 메모는 기본 접힘이다.
5. 마음에 드는 문장을 골라 캐릭터 표정과 함께 카드로 만든다.
6. 현재 계산 결과에서 지원되는 다른 질문을 눌러 읽는다. 같은 출생정보를 다시 입력하지 않는다.

### 친구에게 받은 사용자

1. 친구가 고른 질문과 한 문장이 담긴 카드를 본다.
2. 함께 보낸 링크를 열면 같은 질문이 선택된 시작 화면으로 들어온다.
3. 자신의 출생정보로 자기 결과를 얻는다. 친구의 출생정보·결과를 서버에 저장하거나 URL로 전달하지 않는다.
4. 각자의 결과를 주고받으며 이야기한다. 이 흐름은 두 명의 사주를 판정하는 궁합 기능이 아니다.

### 다시 찾아온 사용자

오늘의 결과를 짧게 확인하거나, 세션에서 읽지 않은 지원 질문을 선택한다. 초기에는 세션의 읽은 질문 ID만 표시하고 장기 결과 보관·알림·수집 등은 실제 흥미 반응을 확인한 뒤 검토한다. 읽지 않았다는 이유로 미지원 질문을 추천하지 않는다.

## 콘텐츠와 화면 편집

다음은 사용자가 원하는 정보를 중심으로 잡은 **개발 목표 질문**이다. 현재 화면에 게시한 문구나 지원 완료를 뜻하지 않는다.

| 우선순위 | 목표 질문 | 필요한 답과 범위 | 현재 상태 |
| --- | --- | --- | --- |
| 1 | 인연은 언제쯤 들어올까? | 원국·대운·세운·월운의 관계 관련 해석상 신호와 대상 기간. 실제 만남 확률·발생일·상대 신상은 계산하지 않는다. | 검토된 시기 규칙 필요 |
| 2 | 취업운은 언제쯤 풀릴까? | 구직에 관한 기간별 신호와 준비/행동. 실제 합격 보장은 제공하지 않는다. | 검토된 취업 시기 규칙 필요 |
| 후속 | 올해 이직해도 괜찮을까? | 사용자의 목표와 직장 변화 관련 신호. 사주만으로 퇴사나 회사 선택을 결정하지 않는다. | 질문 맥락·규칙 검토 필요 |
| 후속 | 직장에서 인정받는 때는 언제일까? | 책임 증가와 실제 인정·대우를 구별한 기간 해석. 책임을 맡는 성향 설명으로 대신 답하지 않는다. | 검토된 평가/보상 규칙 필요 |

첫 목표는 연애 시기와 취업 시기의 두 질문이다. 답변할 수 없는 목표를 유형 설명으로 돌려 말하지 않는다. 규칙이 검토되기 전에는 개발 목표로만 관리하고 일반 사용자의 선택 버튼으로 노출하지 않는다.

표현의 역할은 기존 `question-reading-v1`의 answer/scene/tradeoff/action과 작은 분석 노트를 따른다. 시기 질문의 answer는 현재 흐름과 해석 대상 기간에 답하고, scene은 가능한 장면의 예시, tradeoff는 함께 확인한 부담/상반된 신호, action은 그 기간에 점검할 행동을 담는다. 대상 기간·기준 시각·시간대·사실 경로를 추가할 때는 계약과 버전을 함께 설계한다. 강조 답변은 약간 다른 서체, 본문은 고딕, 분석 노트는 작은 정돈된 문체다. 접힘이나 말줄임으로 본문을 숨기지 않는다.

재미는 사용자가 실제로 궁금한 일과 시기를 중심으로 만든다. 생활 장면과 비유는 답변을 이해시키는 보조 표현이다. 문장의 재미나 표정을 먼저 바꾸는 일을 시기 분석 보강보다 앞세우지 않는다. 설명 방식이 재미있어도 claim의 범위와 종류를 바꾸지 않는다.

도깨비는 시작·질문·결과·공유에서 일관된 반말을 사용한다. 고백·일·계획 등 장면에 맞는 표정은 표시 설정으로 관리하고, 선택한 표정을 보존한다. 표정만으로 좋은 운/나쁜 운을 새로 판정하지 않는다. 시비·모욕·공포·공격적인 훈계는 제외한다.

## 구현 단계와 완료 조건

| 단계 | 작업 | 산출물과 완료 조건 |
| --- | --- | --- |
| 0. 진입 문구 정리 | 유형/성격 질문을 삭제하고 기존 운세 주제만 표시한다. | KO/EN에 거부된 질문이 없고 기존 주제 입력·결과 경로가 이어진다. 미래 사건 기능이 구현됐다고 표시하지 않는다. |
| 1. 답변 명세 | 연애 시기·취업 시기에 대해 사용자가 원하는 정보, 대상 기간, 필요한 사실, 허용/금지 claim, 누락 처리를 정의한다. | 시기 질문을 성향 해석으로 바꿔 답하지 않는다. 각 목표에 규칙·자료·전문가 검토 요구가 명시된다. |
| 2. 기간 사실과 해석 규칙 | 기존 기간/대운 계산에서 재사용할 부분과 추가할 세운·월운 사실을 점검한다. 출처·조건·예외·상반된 신호·시간 미상 처리를 가진 질문별 규칙을 검토한다. | legacy 계산 보호, 기준 기간 경계 회귀, 전문가 검토와 한계 기록. LLM과 휴리스틱 점수가 좋은 사건 날짜·확률을 생성하지 않는다. 미검토 규칙은 draft다. |
| 3. 질문별 결과와 공개 | 아래의 질문별 선택 계약을 추가하고, 검토된 규칙의 조건에서만 두 목표 질문을 공개한다. | 현재 흐름·대상 기간·해석 이유·행동이 같은 사실을 사용한다. 기존 API 필드를 보존하고 정보 차이가 있는 질문만 ready로 둔다. |
| 4. 공유와 사용자 확인 | 서버가 허용한 문장 선택 PNG와 공개 주소의 질문 ID 재진입을 보강한다. 사용자의 답변 만족을 확인한다. | 핵심 조건·기간·한계를 보존하고 출생정보를 URL에 넣지 않는다. 실제 결과와 공유/복귀를 확인한다. 사용자가 얻은 정보를 자기 말로 설명할 수 있는지 기록한다. |

첫 기능 보강은 단계 1~3의 두 목표 질문이다. 질문 목록 수와 카드 디자인은 그 답을 실제로 제공할 수 있게 된 후 확장한다. 현재 기능의 전면 문구를 미래형으로 바꾸는 일을 시기 질문의 완료로 계산하지 않는다.

## 변경하기 쉬운 내부 구조

기간 사실 계산, 검토된 해석 규칙, 질문별 선택, 문구와 표시를 다음 책임으로 분리한다. 기존 엔진과 계약에서 재사용하는 범위를 먼저 정한다.

| 책임 | 데이터/작업 | 단독 작업의 경계 |
| --- | --- | --- |
| 공개 질문 정의 | 안정적인 question ID, topic, KO/EN 제목, 지원 상태·조건, 다음 질문 후보 | backend의 공개 목록을 frontend가 표시한다. 구현 규칙·출생 데이터는 공개 목록에 넣지 않는다. |
| 해석 규칙 | 필요한 fact, 선택 조건, 제외 조건, source/rule/version, 허용 claim | 계산 결과를 읽는 순수 서비스와 검토된 카탈로그. UI·공유·다른 에이전트를 호출하지 않는다. |
| 표현 | answer/scene/tradeoff/action, 같은 규칙의 분석 노트, 공유 허용 문장 | 문구와 KO/EN 검토. 지식/규칙 버전과 별도 copy version으로 관리한다. |
| 표시 설정 | 캐릭터 표정, 타이포그래피, 카드 배치·버튼 문구 | 기존 `experienceCopy.ts`, `experience.css`, 표현 카탈로그. 새로운 명리 판단을 하지 않는다. |
| 검증 | 고정 입력·질문·사실·결과 artifact → 독립 검토 | 기존 사용자·답변·감독 작업을 각각 실행할 수 있게 유지한다. |

JSON/Git 기반 카탈로그를 계속 사용한다. DB·벡터 검색·CMS는 이번 규모에 필요하지 않다. Codex는 편집·검토를 돕고 결과 생성에 필수로 추가하지 않는다. 흥미를 위해 클릭마다 새로운 모델 호출이나 계산을 만들지 않는다.

단계 3의 질문별 계약은 작은 추가 변경으로 설계한다. 선택 질문 ID는 optional로 추가하고 생략 시 기존 경로를 유지한다. 새 질문의 결과를 기존 topic 카드에 덮어써 계약을 바꾸지 않으며, 별도 선택 질문 결과를 추가한다. 현재 loader의 topic 중복 조건을 전역으로 풀지 않고 질문별 선택기를 구분한다. 구형 입력·응답의 호환 검증과 새 format/version 기록이 완료된 후 활성화한다.

실행 단위는 콘텐츠/규칙, UI, 공유, 검증 각각이다. 한 에이전트가 한 입력 계약과 소유 파일만으로 완료할 수 있게 나눈다. 여러 역할의 동시 실행은 필수가 아니다.

## 검증과 판단 기준

자동·런타임 검증:

- 기존 계산/legacy 기준과 출생지·시간 미상 규칙을 보호한다. 생성 출력에 사실·규칙·문구·질문 ID·공유 문장의 정합성을 검사한다.
- 질문 변경 시 정상·반대 사실·누락·미상·critical uncertainty·미지원·KO/EN·변조를 확인한다. 오늘의 결과에는 기준 날짜와 기존 period-flow 사실 비교를 추가한다.
- 실제 변경 단계에서 관련 API 테스트, 웹 타입/빌드, `scripts/verify-web-reading.cjs`, fallback-only `pnpm verify:user-story`를 실행한다. 브라우저는 선택 → 입력 → 실제 결과 → 다른 질문 → 공유 → 복귀까지 확인한다.
- known lunar day-30의 422 FAIL은 기능 과제에 남긴다. 정상 경로 시범이 통과해도 이 문제를 완료로 기록하지 않는다. 이번 진입 문구 정리는 미래/시기 규칙의 런타임 검증을 의미하지 않는다.

합성 역할 검토:

- 사용자 역할: 무엇이 궁금해졌는지, 무슨 답을 얻었는지, 기억/공유하고 싶은 정확한 문장이 무엇인지, 반복된 부분은 무엇인지 검토한다.
- 답변 역할: 같은 동결된 사실·규칙으로 표현을 작성한다. 새 판단을 만들어 흥미를 높이지 않는다.
- 감독 역할: 질문 약속과 결과 범위, 사실·규칙 연결, 예시/조언 구분, 분석 노트와 공유의 의미 보존을 검토한다.
- 코드 FAIL은 긍정적인 흥미 평가로 상쇄하지 않는다. fixture는 구조 검증이며 의미/흥미 검토는 HOLD다. 실제 Codex의 합성 평가는 실제 사용자 결과와 구별한다. 세 역할을 이번 계획 작성 중 새로 실행하지 않았다.

실제 사용자 확인:

5~8명에게 각자 궁금한 질문 하나를 고르게 하고 읽은 뒤 “어떤 답을 얻었는가?”, “친구에게 보내고 싶은 문장은?”, “다음에 어떤 질문을 보고 싶은가?”를 확인한다. 이는 초기 질적 점검이며 시장 전체 반응의 추정 표본이 아니다. 흥미와 유용성의 목표는 사용자가 선택 질문에 대한 답을 자기 말로 설명하고 구체적인 문장을 고르는 것이다.

선택/입력 완료/결과 열람/공유 시작·저장·복사/다음 질문 선택을 구별한다. native 공유창 호출 성공을 상대 수신이나 실제 전송 완료로 기록하지 않는다. 클릭 수나 체류 시간으로 사주 예측의 적중을 판단하지 않는다. 초기에는 관찰 기록과 세션 이벤트로 충분하며 계정·장기 행동 추적·출생정보가 포함된 분석 로그는 도입하지 않는다.

## 보강을 위해 별도 검토할 질문

만남 시기, 취업·승진·대우 시점, 타인 대비 운의 순위는 [읽기 에이전트 계약](../ai/SAJU_READING_AGENT.md)의 미지원 범위를 유지한다. 새로운 질문을 지원할 때 필요한 계산 사실·검토된 규칙·예외·자료를 먼저 갖춘다. 흥미 위주라는 이유로 확률·랭킹·확정 날짜를 추가하지 않는다.

현재 수행한 일은 진입 문구 정리와 계획 개정이다. 첫 미래 질문 기능의 완료는 연애/취업 시기 질문에 필요한 기간 사실·검토된 규칙·결과·한계와 실제 동선이 검증된 상태다. 문구 제거, 기존 대운 카드, 합성 에이전트의 흥미 평가는 새 시기 기능의 완료를 뜻하지 않는다.

개정 2 검증: 웹 타입체크/빌드와 helper 10개 통과. 새 IAB 탭의 390px 화면에서 KO/EN 유형 문구 제거와 KO 네 메뉴의 입력 진입을 확인했다. 임시 viewport와 언어를 복원했다. fallback-only HTTP 사용자 시나리오는 456 PASS / 3 WARN / 1 FAIL이며 기존 유효한 음력 30일의 422가 남는다. WARN은 대운 십성의 사용자 검토·실사용자 흥미·실제 LLM 의미 정확도다. 검증 JSON과 화면은 기존 등록된 `.dev-runtime/agent-verification-20261005/`에 보존했다. 원래 IAB 탭은 연결 오류 페이지에 머물러 복구되지 않았으며 새 검증 탭에서 확인했다. 새 시기 기능·실사용자 흥미·실제 LLM 평가는 수행하지 않았다.
