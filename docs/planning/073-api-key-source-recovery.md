# 073. 기존 API 키 읽기 경로와 상용 연결 복구 진단

## 목표·범위

2026-10-22 사용자는 기존 API 키를 읽지 못하는 원인을 먼저 찾아 상용 모델 연결을 복구하도록 요청했다. 작업은 인증 설정과 실행 경로 진단이며, 계산·판단·문구·공급자 교체나 최신 로컬 변경 전체 배포는 범위에 포함하지 않는다. 키 값은 출력·증거 파일·Git에 기록하지 않는다.

**상태: Blocked. 로컬의 키 설정 부재와 상용 런타임의 키 누락을 새로 확인했으나, Vercel 환경변수 조회 403 때문에 설정 복구와 실제 GPT-5.4 생성은 미완료다.**

Vercel 플러그인의 권한 상태는 기본 `Allow low-risk actions`, 개별 `Use my default`다. 이 정보만으로 403의 원인을 앱 승인 설정이나 Vercel 계정 권한 중 하나로 확정하지 않는다. 권한 변경·재인증·새 CLI 설치·다른 인증 저장소 탐색·비밀 추출은 하지 않았다.

## 현재 Production 실제 요청

기존 주소 `https://saju2604.vercel.app/api/health`는 HTTP200/`ok`다. 기존 임의 입력인 1993-04-22 03:40 남성/제천으로 `/api/saju/preview`에 POST **1회**, 재시도 **0회**를 보냈다. 현재 입력의 실제 연결 상태 확인이며 일반 회귀를 위한 유료 provider 호출이 아니다.

2026-10-22 12:20:53 KST의 응답은 HTTP200, `provider=fallback`, `model=fallback`, `configured_provider=openai`, `final_provider=fallback`, `fallback_reason=missing_api_key`, 경고 `openai_api_key_missing`, `attempts=[]`다. 실제 OpenAI 호출 시도는 0회다. 응답 SHA256과 최소 진단 메타데이터만 보존했으며, 대체 풀이를 GPT-5.4 결과로 게시하지 않았다.

현재 원인은 **키가 상용 런타임에 전달되지 않는 상태**까지 확인됐다. 대시보드 미등록, Production 적용 범위 누락, 변경 후 배포 미반영 중 어느 원인인지는 접근 권한이 없어 미확정이다. 키의 만료·잘못된 값으로 발생한 upstream 인증 거절이라는 증거는 없다.

## 복구를 이어갈 조건

1. 같은 `signous / saju_2604` 프로젝트의 환경변수를 확인·수정할 수 있는 공식 접근이 필요하다. 사용자는 키 위치를 잊었다고 응답했으므로 기억해내라고 반복 요구하지 않는다. 키를 채팅에 보내도록 요청하지 않는다.
2. 접근 가능해지면 `OPENAI_API_KEY`의 등록 여부, Production 적용 범위, 현재 배포에 반영됐는지 먼저 확인한다. 기존 유효 키가 있으면 해당 설정을 복구한다. Secret은 저장 후 읽을 수 없는 경우가 있으므로 원문 복구를 보장하지 않는다.
3. 설정 반영이 필요하면 기존 상용 코드/배포 기준으로 재배포 여부를 검토한다. 로컬에 쌓인 미검토 제품 변경을 인증 복구와 함께 일괄 배포하지 않는다.
4. explicit OpenAI/GPT-5.4의 실제 응답에서 provider/model/diagnostics 성공을 확인한 후에만 복구 완료로 표시한다. 환경변수 등록 또는 HTTP200만으로 완료 처리하지 않는다.

[Vercel 공식 환경변수 문서](https://vercel.com/docs/environment-variables)는 환경변수 변경이 기존 배포에 소급되지 않고 새 배포에 적용됨을 안내한다. [OpenAI 공식 API 키 문서](https://developers.openai.com/api/docs/guides/production-best-practices#api-keys)는 키를 환경변수/비밀 관리 서비스로 공급하고, 만료·교체를 별도로 관리하도록 안내한다.

## 검증·보존

- 관련 provider 단위 테스트 **8 PASS**, 진단용 로더 **5 PASS**, 실행 위치 검사 **2개 일치**.
- fallback-only 사용자 시나리오는 실행했으나 로컬 API8000/Web5173 비응답으로 **BLOCKED**, PASS/WARN/FAIL 모두0. 과거456 PASS/3 WARN/음력30일 FAIL1을 이번 검증 결과로 재사용하지 않는다.
- 첫 진단 실행의 없는 가상환경 경로와 Windows cp949 Git 출력 디코딩 오류는 진단 도구 단계의 실패였다. 프로젝트의 실제 Python 경로/UTF-8 지정으로 수정 후 재실행했다. 제품 오류나 테스트 성공으로 혼동하지 않는다.
- 제품 코드·실제 env 파일·전역 설정·Vercel 환경·권한·배포·서버 변경0. 기존 결과와 사용자 테스트 환경은 그대로 보존한다.
- 현재 스레드 소유 등록 root `.dev-runtime/api-connection-recovery-20261022/`에 최소 진단 JSON·관련 테스트 로그·재실행 방지 1회 요청 영수증을 보존한다. 별도 thread ledger에 임시 root를 등록했으며 사용자 정리 요청 전까지 유지한다. 기존 다른 스레드 산출물을 새 소유물로 등록하지 않는다.

## 2026-10-23 Codex 전환 전후 이력 확인

사용자는 Codex로 테스트하도록 요청한 뒤부터 API가 안 된 것이 아닌지 지적했다. 현재 키 누락만 반복하는 대신 Git 변경과 해당 요청의 실제 실행 기록을 읽기 전용으로 대조했다.

- 최초 Codex provider 추가 커밋은 `2826b90`(6/20)이다. 전후 diff에서 OpenAI 기본값, `OPENAI_API_KEY` 이름, 두 로컬 env 로딩 경로는 유지됐다. OpenAI 분기를 제거하지 않고 Codex 분기를 추가했다.
- 공식 대화 도구로 「사주 풀이를 재미있게 만드는 말투 추천」의 50개 턴을 해당 요청까지 확인했다. 10/5 22:37:55 KST의 사용자 요청 턴 `01a10c49-0aee-7ca3-af61-ae6443301ee8`에서 로컬 Codex6.1/xhigh 프로필 생성과 실행이 확인됐다.
- 그 턴의 명령 `exec-c7e0adad-f1cc-4311-854a-574d0af40f0a`는 API `.env.local`이 이미 있으면 예외로 중단하도록 검사했고 exit0으로 끝났다. 뒤의 실제 fileChange `exec-cb4d7524-4173-4a5c-b8de-1e7f3589855c`는 해당 파일을 `add`로 생성했다. 내용은 Codex 설정이고 `OPENAI_API_KEY` 항목은 없었다. **이 파일 쓰기가 기존 키 파일을 덮어썼다는 증거는 없으며, 해당 단계에서는 파일 부재 확인 후 새로 생성한 기록이 있다.**
- 현재 Production 별칭을 공식 Vercel 도구로 다시 조회했다. 배포 ID는 `dpl_CA8Q45X6m9Kka7mGGnRkBPyQ5dWN`, READY/production, 커밋 `8fd02a67e4ffe7d84439ca82c6d5b9a826c371ec`(8/25)로 이전 관측과 같다. 10월 Codex 로컬 설정 커밋이 현재 상용 주소에서 실행되고 있는 것은 아니다.

따라서 **Codex 요청 뒤 로컬 실행이 전환된 사실은 확인**됐지만, 그 전환이 현재 상용 서버의 `missing_api_key`를 만들었다고 확정할 수는 없다. 당시 다른 프로세스 환경에만 있던 키가 재시작 때 전달되지 않았는지는 과거 프로세스 환경 자료가 없어 미확정이다. 이 가능성과 과거 상용 성공을 부정하지 않는다. 상용 환경변수 등록·범위·현재 배포 반영 상태는 여전히403으로 확인되지 않았다.

현재 스레드 등록 root의 `codex-switch-audit-20261023.json`에 명령/변경의 식별자와 최소 메타데이터만 보존했다. 키 값·전체 대화·내부 추론은 기록하지 않았다. 이번 추가 확인의 새 모델 호출/생성 POST/제품 코드/env/배포 변경은 모두0이다. 제품 수정이 없어 테스트를 재실행하지 않았으며 전날의 검증 성공과 BLOCKED를 새 성공으로 표시하지 않는다. **이력 확인은 완료됐으나 상용 연결 복구는 여전히 Blocked다.**
