# 039. 기간별 운세 지수 설계

작성일: 2026-10-06. 개정 2: 대략적인 지수와 기본 접힘의 상세 근거 데이터로 제품 방향을 구체화했다. 상태: **설계 제안 / 지수 산식·규칙 검토 필요**.

사용자 요청: “사람들은 운세가 얼마나 좋은지 수치로 알고 싶어해. 운세 지수 처럼. 이걸 어떻게 만들 수 있을까”. 이는 제품 소유자의 요구이며 모든 사용자에 관한 조사 결과는 아니다. 이번 작업은 코드·자료 분석과 설계 문서화다. 숫자 노출, 계산 정책, 모델, API, 공유 화면은 변경하지 않았다.

최신 보정: “정확한 것은 만들 수 없어보여 대충적되 근거데이터를 펼치기로 볼 수 있어야해. 예로들면 도화선이 남들보다 많도ㅠ이 확률은 어떻다 뭐 이런식으로.” 문맥상 “도화선”은 도화살로 이해한다. 사용자는 대략적인 해석 지수와 실제 계산 근거의 확인을 우선하며, 실증 예측 모델의 완성을 첫 출시 조건으로 요구한 것은 아니다. 지수의 정확한 예측력과 별개로 개수/위치/계산 기준은 충실하게 제공한다. 근거 없는 비교 숫자나 사건 확률을 만들어 넣지는 않는다.

## 목표와 지수의 의미

**오늘 또는 이번 달의 특정 주제에 관해, 프로젝트 해석 규칙이 판정한 유리함과 부담을 100점 척도로 요약한다.** 이름은 “오늘의 운세 지수”, 분야는 연애·직장·금전으로 제안한다. 동일한 입력·대상 시각·계산/규칙/척도 버전이면 같은 지수가 나온다.

75점은 75%의 사건 발생 확률, 인구 상위 25%, 전문가 검증 정확도, 인생 전체의 등급을 뜻하지 않는다. 제안 지수는 서비스 자체의 해석 지표다. 날짜별 비교도 동일한 척도·지원 범위에서만 한다. 실제 만남·취업·승진 날짜를 숫자로부터 도출하지 않는다. 기존 038의 미래 질문 규칙 개발은 별도로 필요하다.

## 조사에서 확인한 제품 형식

2026-10-06 확인한 [포스텔러의 개발사 Google Play 설명](https://play.google.com/store/apps/details?hl=ko&id=com.un7qi3.forceteller)은 매일의 운세 점수와 1일/30일/6개월 단위 조회를 소개한다. 이는 날짜별 숫자 제공 사례이며 숫자가 인기의 원인이라는 증거나 예측 정확도 검증이 아니다.

[포스텔러 배우자운 소개](https://forceteller.com/item/75)는 오행의 점수·위치·충합·강약 등을 고려한다고 설명한다. 공개 설명에는 재현 가능한 전체 산식·가중치·검증 결과가 없다. 경쟁사의 비공개 점수나 실제 예측력을 추정하지 않고 우리 출처·범위·계산을 기록한다.

## 계산 구조와 모듈 경계

```text
기존 계산 엔진
  → 불변 명식/기간 사실 snapshot
  → 지수 규칙 매칭: 유리한 신호 / 부담 신호 / 보류 이유
  → 분야별 점수 집계 + 근거 trace + 지원 상태
  → 서버 응답
  → UI의 지수·한 줄 해석·작은 분석 노트·공유
```

지수 모듈은 순수 함수로 snapshot과 버전이 고정된 규칙을 받는다. HTTP·설정·LLM·React·문구 번역에 의존하지 않는다. 코드가 판정/점수를 소유하고 모델은 서버가 허용한 판정의 문장화만 맡는다. 지수 전용 규칙 카탈로그와 기존 문장 카탈로그는 분리한다.

| 계층 | 제안 책임 |
| --- | --- |
| period fact adapter | 대상 시각/시간대, 일·월·년 간지, 원국과의 관계, 실제 활성 대운, 불확실성·가용 입력을 구조화한다. 누락을 placeholder로 확정하지 않는다. |
| index knowledge | 출처, 적용 주제, 조건, 제외 조건, 관계의 위치, 상반된 신호 처리, 가중치 검토 상태를 관리한다. |
| index evaluator | 조건에 맞는 규칙과 fact refs를 선택한다. 같은 원인의 중복·상쇄/충돌·가용 범위를 처리한다. |
| index aggregator | 정해진 척도로 집계한다. 유리함/부담의 각 기여와 최종 지수를 반환한다. |
| index presenter | 지수 구간과 실제 기여에 대응한 한 줄 해석·노트를 선택한다. LLM 없이 기본 결과를 표시할 수 있게 한다. |

추가할 파일명·API 경로는 구현 시 확정한다. 기존 `analyze_saju`, `PeriodFlow`, 공개 점수 필드의 의미를 덮어쓰지 않는다. 종합 신강·용신 판단이 필요한 규칙은 현재 계산이 제공하는지 먼저 확인한다. 없으면 해당 규칙을 보류하거나 입력/판정 계층을 별도 검토한다.

## 규칙 지식의 필수 필드

`rule_id`, `topic`, `period_scope`, `source_id`, `source_location`, `source_scope`, `review_status`, `required_fact_paths`, `conditions`, `exclusions`, `direction`, `weight`, `evidence_family`, `family_cap`, `conflict_policy`, `allowed_claims`, `rule_version`을 제안한다.

- 조건이 어떤 주제의 유리함/부담을 뜻하는지, 적용 위치와 예외까지 설명할 수 있어야 한다.
- `draft` / 검토 누락 / 필요한 사실 누락 규칙은 공개 집계에서 제외한다. 모든 규칙이 제외되면 50점을 반환하지 않고 보류한다.
- 프로젝트 편집 승인, 전문가 검토, 실제 사건에 대한 실증 검증을 서로 다른 상태로 기록한다.
- `knowledge_version`, `rule_version`, `scale_version`, `copy_version`, `format_version`을 독립 관리한다. 가중치/집계 변경은 rule/scale 변경이며 문구 변경으로 숨기지 않는다.

## 집계 방식 제안

가장 먼저 유리함과 부담을 설명할 수 있는 규칙을 검토한다. 그 다음 각 규칙의 기여를 정한다. 신호 개수만 세거나, 결과가 재미있도록 매번 가중치를 바꾸지 않는다.

### 수치의 객관성: 2026-10-06 추가 질문

사용자는 “수치를 어떻게 객관적으로 표현할 수 있어?”라고 물었다. 현재의 50점 기준·가감점·5점 표시 단위는 설계자가 제안한 척도이며 실제 운의 측정 결과가 아니다. 산식을 고정하거나 AI 대신 코드로 계산한다고 객관적인 사건 예측이 되는 것은 아니다.

| 검토 대상 | 확인할 방법 | 통과해도 뜻하지 않는 것 |
| --- | --- | --- |
| 계산의 재현성 | 같은 명식 snapshot·대상 기간·규칙/척도 버전의 출력과 근거가 동일한지 검사 | 실제 좋은 일의 예측 정확도 |
| 해석 기준의 일관성 | 출처/조건/예외 기록, 독립 전문가의 동일 사례 눈가림 판정과 불일치 기록 | 전문가 의견 일치가 실제 사건을 증명한다는 주장. Codex 역할 검토는 전문가 검토의 대체가 아니다. |
| 척도의 안정성 | 근거 있는 가중치 후보·그룹 cap·집계법을 바꿨을 때 점수/순서의 민감도 검사 | 임의 가중치가 객관적 사실이라는 주장. 요인분석이나 정규화도 의미의 타당성을 자동 보장하지 않는다. |
| 실제 결과와의 관계 | 사건 정의·관측 기간을 먼저 정하고, 예측을 사전 고정한 뒤 별도 관측 결과와 비교 | 단순한 상관이나 사용자 만족을 사주의 인과효과/정확도로 취급 |

[OECD/JRC 복합지표 방법론](https://www.oecd.org/content/dam/oecd/en/publications/reports/2008/08/handbook-on-constructing-composite-indicators-methodology-and-user-guide_g1gh9301/9789264043466-en.pdf)은 지표 선택·정규화·가중치·집계에 판단이 개입하므로 선택을 문서화하고 불확실성/민감도를 검토하도록 설명한다. 이 일반적인 방법을 운세 지수의 투명성과 안정성 검토에 적용하는 것은 설계 제안이며 사주가 검증된 지표라는 뜻은 아니다.

초기에는 “객관적인 운의 크기” 대신 **명시한 규칙으로 산출한 해석 지수**로 표시한다. 75와 60의 차이는 이 척도에서 15점이며 운이 25% 좋아졌다는 뜻이 아니다. 5점 단위나 구간 표현도 가중치 선택 문제를 해결하지 않는다.

같은 사용자의 기간 비교를 추가할 때는 대상 기간·주제·지원 범위·계산/규칙/척도 버전을 고정한다. 예를 들어 “오늘 75 / 직전 30일 해석 지수 평균 60”은 형식을 설명하는 가상 예시다. 실제로 동일 조건의 전체 날짜를 계산한 경우에만 평균과 차이를 표시한다. 기간 변경 시 비교 기준을 표시하고 누락 날짜를 유리하게 제외하지 않는다. 이것도 서비스 지수의 비교이며 인구 순위·실제 만남 가능성·좋은 사건 날짜가 아니다. 휴리스틱 점수를 percentile로 정규화하지 않는다.

실제 사건과의 관계를 검증하려면 “연애운 좋음”처럼 모호한 결과를 먼저 좁힌다. 후보는 일정 기간의 새로운 첫 만남 발생 여부, 면접 제안 수신 여부, 보상 변경 여부 등이다. 사건별로 목표가 다른 사용자를 섞지 않고 조건과 관측 기간을 사전에 정한다. 지원 횟수·구직 상태·관계 상태·요일/계절 등 행동/상황 요인이 함께 달라질 수 있다는 점을 고려한다.

수집/검증 계획은 다음 요구를 갖는다. 실제 수집이나 검증은 이번 작업에 포함하지 않는다.

1. 사건이 일어나기 전에 지수·버전·대상 기간을 고정한다. 사건을 본 뒤 산식이나 성공 기준을 바꾸지 않는다.
2. 관측 동의·자료 범위와 누락/이탈 처리를 정한다. 점수를 보여줘 행동이 달라지는 효과와 예측력을 구별할 수 있게 눈가림 검토 등을 설계한다.
3. 규칙 개발 자료와 검증 자료를 사람/시간 기준으로 분리한다. 같은 사람의 반복 기록과 미래 정보가 평가 자료에 새지 않도록 한다.
4. 단순 사건 기저율, 요일/계절, 행동/상황 기반 기준 모델과 비교해 사주 지수가 별도로 정보를 더하는지 확인한다. 실패/반례·표본 불확실성도 보고한다.
5. 검증을 통과한 사건·대상 집단·기간 밖으로 결과를 확대하지 않는다. 흥미나 만족 응답만으로 사건 예측 검증을 통과시키지 않는다.

관측 자료가 없으면 “좋은 사건 확률”이나 인구 대비 순위는 제공할 수 없다. 향후 충분한 자료로 별도의 예측 모델을 만들더라도 기존 휴리스틱 값을 퍼센트로 바꾸는 작업과 구별한다. 확률을 주장하려면 독립 평가에서 예측한 확률대와 실제 사건 빈도가 일치하는지 확인해야 한다. [scikit-learn 확률 보정 문서](https://scikit-learn.org/stable/modules/calibration.html)는 이 원리와 독립 보정 자료 요구를 설명하며, Brier 점수 하나만으로 확률 보정이 입증되지는 않는다고 명시한다. 이 방법론은 현재 사주 지수의 검증이나 공개 확률 사용을 승인하지 않는다.

초기 **제품 척도 후보**는 다음과 같다. 명리의 표준 공식이나 검증된 수치가 아니다.

```text
분야별 raw = 50 + Σ(근거 그룹별 제한을 적용한 signed contribution)
표시 지수 = raw를 5점 단위로 반올림한 값
```

- 50은 이 척도의 중립 기준이다. 인구 평균이나 사건의 50% 확률을 뜻하지 않는다.
- 같은 원인에서 파생된 규칙은 한 그룹으로 묶어 중복 가점을 제한한다. 그룹별 ±기여 상한과 전체 범위는 척도 검토에서 확정한다.
- 초기에는 5~95 범위를 제품 척도 후보로 검토한다. 0/100을 사건 불가능/성공 보장으로 오해하게 만들지 않는다. 이 범위도 정확도를 증명하지 않는다.
- 점수 계산 전에 최소 근거/가용 범위/계산 불확실성 gate를 통과해야 한다. 누락 정보를 감점하거나 가용 가중치를 임의 재정규화하지 않는다.
- 유리한 신호와 부담이 함께 큰 경우에는 중간 점수만 보여 상황을 숨기지 않는다. 같은 결과에서 두 신호와 주의점을 설명한다.
- 분야별 지수 먼저 개발한다. “종합 1점수”는 모든 필수 분야가 동일한 범위와 버전으로 지원된 뒤 고정된 집계 방식을 검토한다. 일부 분야가 보류됐다고 나머지 평균을 종합 지수로 표시하지 않는다.
- 1점 단위/소수점·“정확도 93%”·인구 순위는 도입하지 않는다. 그래프를 예쁘게 만들려고 날짜별 jitter나 표본 percentile을 적용하지 않는다.

가중치는 규칙별 대조 사례와 근거 검토로 정하고, 분포·민감도 검사로 과도한 포화나 단일 항목 지배를 확인한다. 합성 사례의 분포가 넓고 예쁘다는 사실을 좋은 운의 실증 검증으로 취급하지 않는다.

## 응답 계약과 불확실성

제안 계약은 `fortune-index-v1`. 각 주제는 다음 필드를 갖는다.

```text
topic, period_start, period_end, as_of, timezone_id
status: ready | limited | needs_rule_review | insufficient_facts | critical_uncertainty
value: 정수 또는 null, scale_max: 100
scope, label, supportive_signals, caution_signals
matched_rule_ids, fact_refs, contributions, exclusions
calculation_version, knowledge_version, rule_version, scale_version, copy_version
review_status, empirical_validation_status
```

`ready`는 이 서비스의 명세에 따라 계산 가능하다는 상태다. 전문가 검증/사건 예측 정확도 인증을 뜻하지 않는다. 현재 구현 상태는 `needs_rule_review`이며 새 숫자를 반환하지 않는다.

출생시간 미상은 시주/대운 없는 별도 지원 범위로 처리한다. 검토된 부분 지수가 가능하다면 `limited`와 같은 범위의 별도 척도를 사용하고 전체 지수와 비교하지 않는다. 부분 척도 자체가 없으면 `value=null`이다. 결과가 달라질 수 있는 경계/critical uncertainty는 점수 산출을 보류한다. 동일 snapshot에서 언어·모델·표정·문구를 바꿔도 값이 바뀌지 않아야 한다.

## 모바일 표시와 문장 계약

아래는 **화면 형식의 가상 예시**이며 실제 계산 결과/검토된 규칙의 답이 아니다. 지수와 주요 한 줄은 바로 보여주고, 상세 근거 데이터는 기본 접힘으로 제공한다.

> 오늘의 연애운 **75 / 100**
>
> 오늘은 대화의 물꼬를 트는 쪽에 힘이 실려 있어.
>
> 다만 반응까지 미리 결론 내리지는 마.

날짜와 지수를 먼저, 판정의 직접 설명을 다음으로, 유리함/부담과 한 행동을 이어서 표시한다. 기존 도깨비·명조 강조 체계를 재사용한다. 선택 사실과 해석, 새 상세 데이터는 작은 **풀이 메모**를 눌러 연다. 사용자가 거부한 “근거 데이터 보기”나 꼭 봐야 할 듯한 호기심 문구는 쓰지 않는다. 이 최신 요청은 새 지수의 상세 근거를 항상 노출하던 제안을 대체한다. 2026-10-07 기존 분석 노트의 문구/접힘은 구현했지만 지수와 새 상세 데이터 응답/화면은 아직 미구현이다. 본문은 계속 바로 표시한다.

펼친 영역은 확인된 값, 개수/위치, 계산 기준, 점수 기여, 비교 자료가 있다면 자료 범위/빈도를 순서대로 보여준다. 전문 용어에는 한 줄 설명을 붙인다. 지수 판단과 관계없는 신살을 모두 나열하거나 개발용 ID만 표시하지 않는다. 결과/주제 변경 시 닫힘으로 초기화하고, 키보드·스크린리더에서 작동하는 details/summary 또는 동등한 disclosure를 사용한다.

지수 가까이에 짧은 정의 “사주 흐름을 요약한 해석 지수”를 둔다. 공유 카드도 주제·대상 날짜·지수·이 정의를 보존한다. 친구 점수보다 높다는 이유로 더 좋은 인생/더 높은 만남 확률이라고 말하지 않는다. 낮은 지수의 문구는 부담과 가능한 행동을 설명하며 모욕·겁주기·액운 확정을 피한다.

지수를 먼저 빠르게 확인하고 기존 긴 생성이 숫자 표시를 막지 않도록 한다. 이를 위해 계산/지수 응답과 선택적 문장 생성의 호출 경계를 검토한다. 기존 6.1 Sol/xhigh 결과가 277.141초 걸린 관측은 지수 계산 속도 측정이 아니다. 지수 집계에 모델 호출을 추가하지 않으며 실제 계산·응답 지연은 구현 후 측정한다.

### 도화살 상세 근거의 실제 가용 데이터

`ManseSpecialStar`는 이미 `key`, `method_id`, `basis`, `anchor_value`, `target_values`, `count`, `matches`를 제공한다. `matches`에는 기둥/간지/매칭 위치가 있다. 단순히 active label만 모델에 공급하는 기존 `InterpretationSpecialStar` 대신 지수 근거 adapter는 원본 구조를 사용해야 한다.

`calculate_special_stars.py`는 함지도화를 연지 기준과 일지 기준 두 방식으로 계산하며, 왕지도화·목욕도화·홍염도화와 함지도화의 위치 태그를 별도로 관리한다. 코드의 metadata tier/weight는 전문가 승인/통계 가중치가 아니므로 지수 산식에 그대로 사용하지 않는다.

- **함지도화 위치 수**: 선택한 기본 함지도화 방법에서 매칭된 기둥의 합집합을 센다. 연지/일지 기준이 같은 기둥을 가리키면 1곳이다. 각 기준에서 나온 계산 결과는 펼친 영역에 별도 표시한다.
- 왕지도화/목욕도화/홍염은 다른 지표로 표시한다. 함지도화의 위치 수와 합쳐 “도화 총 7개”처럼 부풀리지 않는다.
- 벽내/벽외 등 위치 태그는 기본 도화와 같은 사건 위치를 재설명하므로 독립 개수·가점으로 중복 집계하지 않는다.
- 시간 미상에서는 시주를 제외하고 범위를 명시한다. 없는 결과를 0개로 단정하지 않는다.
- 원국의 신살 개수는 날짜마다 바뀌지 않는다. 해당 기간의 변화 근거는 실제 기간 snapshot/규칙이 별도로 필요하다. 신살 개수만으로 오늘의 만남 시기를 설명하지 않는다.

2026-10-06의 합성 기둥 확인에서 `乙酉/庚辰/壬子/戊午`는 연지 기준 1곳(시주), 일지 기준 1곳(년주)으로 고유 위치 2곳이었다. 별도 합성 기둥 `乙酉/庚辰/丁丑/戊午`에서는 두 방법이 시주를 함께 가리켜 원본 방법별 합계 2가 고유 위치 1이 됐다. 이는 계산 단위의 중복을 확인하는 코드 사례이며 유효 생년월일 표본이나 실제 운세/사건 자료가 아니다. 기존 신살 단위 테스트 5개가 통과했다.

### “남들보다 많다”와 “확률”의 데이터 계약

다음 세 의미를 분리한다.

| 항목 | 표시할 수 있는 수치 | 현재 상태 |
| --- | --- | --- |
| 내 명식의 확인값 | 기본 도화 고유 위치 수, 각 방법의 개수/위치, 제외한 항목 | 원본 계산 데이터 있음; 지수 근거 adapter/UI는 미구현 |
| 비교 자료의 특징 빈도 | 정의한 표본에서 도화 위치 수가 같은/적은/많은 명식의 실제 개수, 자료 범위/수집·계산 방식 | 비교 자료 없음. 숫자/“남들보다 많다” 문장 보류 |
| 실제 관계 사건 확률 | 정의한 기간에 만남 등이 발생한 실제 관측 자료로 독립 검증한 예측 | 자료/모델/검증 없음. 도화 개수나 해석 점수를 성공 확률로 전환하지 않음 |

비교 자료가 준비되면 `reference_id`, `reference_kind`, `sample_count`, `eligible_count`, `sampling_method`, `birth_date_range`, `birth_time_policy`, `calendar_timezone_policy`, `calculation_version`, `feature_definition_version`, `frequency_count`, `frequency_denominator`, `limitations`를 남긴다. 빈도는 비교 자료에 존재하는 명식의 계산 사실을 집계한 값으로만 사용한다. 휴리스틱 지수를 확률/percentile로 변환하는 기능을 추가하지 않는다.

합성 날짜/기둥을 생성한 경우에는 “계산한 비교 명식에서”라고 표시하고 실제 인구나 “남들”의 분포로 소개하지 않는다. 실제 이용자 자료도 모집/동의/선택 편향과 지원 범위를 확인해야 인구에 일반화할 수 있다. 출생일·시간은 균등하지 않고 간지끼리도 독립이지 않으므로 간지 조합의 단순 이론 비율을 사람의 확률로 쓰지 않는다.

“이 표본에서 도화 위치 2곳 이상인 명식이 차지하는 비중”은 특징의 표본 빈도다. “내가 연인을 만날 확률”과는 별개이며 앞의 빈도에서 뒤의 사건 확률을 도출하지 않는다. 이 차이를 펼친 근거의 짧은 설명과 공유의 해당 수치 라벨에 보존한다.

### 지수와 근거 묶음의 제안 계약

기존 지수 응답에 `evidence_summary`와 기본 접힘 패널용 `evidence_details`를 추가하는 방향을 제안한다. 각 항목은 다음 정보를 갖는다.

```text
feature_id, label, kind: calculation_fact | interpretation_contribution | reference_frequency
value, unit, calculation_method, observed_positions, excluded_positions
fact_refs, rule_refs, source_refs, duplicate_group
contribution_points: 검토된 가중치가 있을 때만 정수, 그 외 null
comparison: 기준 자료가 있을 때만 reference_id/분자/분모/범위, 그 외 null
limitation, knowledge_version, rule_version, reference_version
```

개수·비교 빈도·가점은 서로 다른 단위로 표시한다. 가점을 붙였다는 이유로 계산 사실이 더 정확하거나 효과가 검증됐다고 말하지 않는다. 모델이 근거·표본·개수·가점을 생성하지 않게 서버에서 고정한다. 공개 시에는 규칙 일관성·중복 제거·누락 처리·문장 연결을 검증하고 자체 해석 지수라는 정의를 보존한다. 사건 실증 검증은 별도 미완료 상태로 유지한다.

## 구현 순서와 완료 조건

| 단계 | 완료 조건 |
| --- | --- |
| 1. 주제·규칙 명세 | 오늘의 분야별 유리함/부담 정의, 필요한 사실, 출처·예외·검토 상태, 척도/보류 기준을 확정한다. 연애/직장/금전 중 검토 완료 범위만 시범한다. |
| 2. 구조화 사실과 독립 계산기 | 현재 날짜/월 경계와 전체 관계를 snapshot으로 공급한다. 순수 집계 함수는 HTTP·LLM·설정 없이 독립 실행한다. |
| 3. 검증과 지수 응답 | 범위·결정성·기여 합산·중복 cap·반대 사실·충돌·미상·경계·변조를 검사한다. fallback-only 회귀를 포함한다. |
| 4. 모바일 숫자/펼침 근거/공유 | 지수·한 줄은 즉시, 상세 근거 데이터는 기본 접힘. 같은 규칙/고유 위치 수를 사용하고 비교 자료 없는 숫자나 가짜 중립값을 넣지 않는다. 시간 미상·중복·재진입/주제 초기화·접근성을 확인한다. 숫자 표시가 LLM 생성에 의존하지 않는다. |
| 5. 같은 척도의 기간 비교 | 동일 지원 범위/버전에서 과거·미래 날짜별 해석 지수를 계산한다. 날짜 선택/그래프는 이후 범위다. 이를 사건 발생일·택일 인증으로 승격하지 않는다. |
| 6. 실제 사용자 이해 확인 | 점수를 확률이나 인생 등급으로 읽지 않는지, 이유를 이해하는지, 공유/재확인 의도가 있는지 관찰한다. 흥미·이해·규칙 검토·실증 정확도를 별개로 보고한다. |

기존 독립 검증 시스템은 향후 사용자 역할(숫자의 의미 이해), 질의 역할(근거에 일치한 표현), 감독 역할(기여 추적/확률·순위 오해/범위 검토)을 맡을 수 있다. 이번 설계에서는 역할 prompt/rubric나 실행기, 실제 모델 호출을 변경하지 않았다. 구현 시에는 새 계약과 역할 버전을 함께 적용한다.

## 이번 작업의 검증과 남은 일

현재 코드·계약·피드백 정책과 경쟁사 공개 설명을 대조했다. 문서 링크·Git diff를 확인한다. 제품/계산 코드 변경이 없으므로 API·웹 빌드·fallback HTTP 재실행 및 유료/계정 모델 생성은 하지 않는다. 지수 엔진·API·숫자 UI·전문가 검토·실사용자 평가는 미구현/미수행이다. 기존 유효 음력 30일 입력 FAIL은 그대로 남아 있다.
