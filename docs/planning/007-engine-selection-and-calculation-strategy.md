# Engine Selection And Calculation Strategy 007

## 목적
- 사주팔자 계산 엔진을 무엇으로 채택할지 결정한다.
- 왜 그 선택을 했는지와 왜 다른 후보를 메인 엔진으로 쓰지 않는지를 남긴다.
- 이후 개발 재개 시 계산 파이프라인을 다시 해석하지 않고 바로 이어갈 수 있게 한다.

## 최종 결정
- 메인 계산 엔진은 `6tail/lunar` 계열을 사용한다.
- 현재 백엔드 기본 스택이 Python이므로 1차 채택 구현체는 `lunar-python`으로 간다.
- 시간대와 역사 시차 처리는 사주 엔진에 맡기지 않고 `IANA TZDB` 기반의 Python `zoneinfo`로 처리한다.
- 계산 검증용 보조 엔진은 `sxtwl`을 사용한다.
- 점수, 등급, 해석 판단은 우리 코드에서 수행한다.
- LLM은 계산 결과를 문장으로 표현하는 역할만 맡는다.

## 한 줄 결론
`지역 선택 -> IANA timezone 확인 -> 현지 출생시각 검증 -> 양력/음력 정규화 -> lunar-python으로 사주 계산 -> 우리 분석 엔진 -> LLM 표현`

## 이 결론을 내린 이유

### 1. 우리 서비스는 정확도가 최우선이다
- 시간 보정이 틀리면 전체 결과 신뢰도가 무너진다.
- 사용자 입력은 `양력/음력`, `HH:mm`, `성별`, `지역`을 모두 받는다.
- 출생시간 미상일 때 `00:00`으로 진행하더라도 시주 기반 결과는 제한해야 한다.
- 따라서 계산 엔진은 단순 간지 출력이 아니라 절기, 달력 변환, 시간 규칙과의 결합이 안정적이어야 한다.

### 2. 직접 구현은 리스크가 너무 크다
- 연주, 월주, 일주, 시주 계산은 절기 경계와 달력 규칙 때문에 직접 구현 시 오류 가능성이 높다.
- 음력/양력 변환과 윤달 처리까지 직접 소화하면 검증 범위가 과도하게 커진다.
- 우리 서비스의 차별화 포인트는 계산식 재발명이 아니라 `정확한 계산 + 설명 가능한 해석`이다.

### 3. `6tail/lunar` 계열이 현재 요구와 가장 잘 맞는다
- 공개 문서 기준으로 `양력/음력`, `간지`, `절기`, `八字`, `五行`, `十神`을 지원한다.
- 연주와 월주 계산에서 입춘 및 절기 교접 시각 기준 선택지를 제공한다.
- Python 구현체가 있어 현재 FastAPI 백엔드와 자연스럽게 통합할 수 있다.
- Java 구현체도 있어 추후 별도 엔진 서비스로 분리할 여지도 남는다.

### 4. 시간대는 사주 엔진이 아니라 TZDB가 책임져야 한다
- 지역 시차, 역사적 시간 변경, DST는 직접 계산식으로 신뢰할 대상이 아니다.
- Python `zoneinfo`는 IANA time zone database를 사용하므로 이 레이어를 시간 원천으로 삼는 것이 맞다.
- 사주 엔진에는 "이미 검증된 현지 출생시각"만 넣어야 한다.

## 채택 스택

### 메인 엔진
- `lunar-python`
- 역할:
  - 양력/음력 변환
  - 절기 기준 사주팔자 계산
  - 만세력 기초 데이터 생성

### 시간 보정 원천
- Python `zoneinfo`
- Windows 환경 보완용 `tzdata`
- 역할:
  - IANA timezone 확인
  - 역사적 UTC offset 반영
  - DST 존재 여부와 중복 여부 확인

### 검증용 보조 엔진
- `sxtwl`
- 역할:
  - 절기 경계와 특수 날짜에 대한 golden test 교차 검증
  - 메인 엔진 결과의 신뢰성 확인

## 반려 또는 보류한 후보

### 1. 직접 계산 구현
- 반려 이유:
  - 정확도 검증 비용이 너무 크다.
  - 절기, 윤달, 경계 시각 처리에서 오류 가능성이 높다.
  - 유지보수자가 계산 규칙을 계속 이해하고 재검증해야 한다.

### 2. `bazi-calculator-by-alvamind`
- 반려 이유:
  - 공개 README에 `Time zone considerations`, `Lunar calendar approximations`를 한계로 명시하고 있다.
  - 우리 기획의 핵심인 `양력/음력 신뢰성`, `시간 보정 신뢰성`과 충돌한다.
  - 로컬 참고 구현에서는 `calendar_type`과 `minute`가 엔진 계산에 제대로 반영되지 않았다.
  - UTC 기준 시각을 엔진 입력으로 넣는 위험한 사용 방식이 함께 존재했다.
- 결론:
  - 구조 참고용 예제로는 볼 수 있지만 메인 계산 엔진으로는 채택하지 않는다.

### 3. `sajupy`
- 보류 이유:
  - 기능 설명은 매력적이지만 프로젝트 성숙도와 검증 정보가 상대적으로 부족하다.
  - 메인 엔진으로 바로 채택하기보다 비교 후보 또는 실험 후보가 적절하다.

### 4. FortuneFlow 계산 코어 직접 편입
- 보류 이유:
  - 로컬 참조 결과 사주 계산 구조 자체는 참고 가치가 있으나, 시간 보정과 패키징 품질이 서비스 코어로 바로 쓰기엔 애매하다.
  - 일부 구조는 `corrected_solar_date` 같은 전처리 완료 입력을 전제로 한다.
- 결론:
  - 계산 파이프라인 설계 참고용으로만 사용한다.

## 구현 원칙

### 원칙 1. 사주 엔진은 adapter 뒤에 숨긴다
- 서비스 전역에서 오픈소스 라이브러리를 직접 import하지 않는다.
- 엔진 교체 가능성을 남기기 위해 우리 인터페이스를 먼저 만든다.

예시 구조:

```text
apps/api/app/domain/saju/
  schemas.py
  time_correction.py
  calendar_normalization.py
  adapters/
    lunar_python_engine.py
    sxtwl_verifier.py
  services/
    calculate_saju.py
    build_analysis_payload.py
```

### 원칙 2. 시간대 보정과 사주 계산을 분리한다
- `time_correction.py`는 지역, tzid, 역사 시차, DST만 다룬다.
- `calendar_normalization.py`는 양력/음력과 윤달 정규화만 다룬다.
- `lunar_python_engine.py`는 정규화된 입력으로 사주 계산만 수행한다.

### 원칙 3. 엔진 입력은 UTC가 아니라 검증된 현지 출생시각 기준이다
- UTC는 저장과 추적용 메타데이터로만 둔다.
- 사주 계산용 입력은 출생지 기준 현지 시각이어야 한다.
- 엔진에 `year/month/day/hour/minute`, `calendar_type`, `sex`가 명시적으로 전달되어야 한다.

### 원칙 4. 출생시간 미상 정책은 계산 결과에 반영한다
- UI 입력 단계에서 출생시간 미상일 경우 `00:00`으로 받는다.
- 동시에 `is_birth_time_estimated=true`를 남긴다.
- 이 경우 시주 기반 결과는 계산 후 그대로 노출하지 않고 비활성화 또는 제한한다.

### 원칙 5. 판단과 표현을 분리한다
- 오행 점수, 등급, 희귀 조합 판정은 우리 분석 엔진이 담당한다.
- LLM은 주어진 결과를 요약하고 설명만 한다.
- LLM이 새로운 점수나 등급을 만들면 안 된다.

## 권장 계산 파이프라인

### 1. 입력 수집
- `calendar_type`
- `birth_date`
- `birth_time`
- `sex`
- `region selection`

### 2. 지역 정규화
- 자유 입력 텍스트를 직접 저장하지 않는다.
- 자동완성 후보에서 하나를 선택하게 한다.
- 선택 결과는 최소한 아래 값을 가진다.
  - `country`
  - `city`
  - `tzid`

### 3. 시간 검증
- `local datetime + tzid`를 `zoneinfo`로 검증한다.
- 존재하지 않는 시각이면 오류를 반환한다.
- 중복 시각이면 fold 정책을 적용하고 메타데이터에 남긴다.

### 4. 달력 정규화
- 입력이 양력이면 solar 경로 그대로 계산한다.
- 입력이 음력이면 엔진 또는 정규화 계층에서 양력 대응값과 윤달 여부를 명시적으로 확정한다.

### 5. 사주 계산
- `lunar-python` adapter가 4주, 오행, 십성, 대운의 기초 데이터를 만든다.
- 결과는 우리 표준 응답 형태로 정규화한다.

### 6. 시주 제한 처리
- `is_birth_time_estimated=true`이면 시주 의존 필드를 제한한다.
- 사용자 화면에는 제한 안내를 함께 노출한다.

### 7. 분석 엔진
- 점수 계산
- 등급 계산
- 희귀 조합/불균형 플래그
- 근거 요약 생성

### 8. LLM 표현
- 요약
- 강점
- 약점
- 연애운
- 직업운
- 금전운
- 대운 흐름
- 행동 조언

## 개발 규칙

### 규칙 1. 메인 엔진 교체 가능성을 남긴다
- `SajuEngine` 같은 내부 인터페이스를 둔다.
- 초기 구현체는 `LunarPythonEngine`으로 간다.
- 필요하면 이후 `LunarJavaEngine` 또는 다른 구현체를 추가할 수 있게 한다.

### 규칙 2. 엔진 실패 시 조용한 fallback 금지
- 계산 라이브러리 로드 실패 시 대충 숫자 문자열을 돌려주는 방식은 금지한다.
- 엔진 실패는 명확한 에러 또는 검증 실패로 처리한다.

### 규칙 3. 계산 입력 계약을 축소하지 않는다
- `HH:mm`를 받으면 엔진 계층까지 분 단위를 유지한다.
- `calendar_type`을 받으면 엔진 계층까지 유지한다.
- 중간 계층에서 `hour`만 남기거나 `calendar_type`을 버리면 안 된다.

### 규칙 4. 지역은 이름이 아니라 tzid가 핵심이다
- 표시용 지역명과 계산용 timezone 식별자를 분리한다.
- 계산 파이프라인의 기준값은 `tzid`다.

## 테스트 전략

### unit
- 시간대 정규화
- DST 존재/중복 처리
- 양력/음력 정규화
- 시주 비활성화 규칙
- 분석 엔진 점수/등급 함수

### integration
- 입력 -> 시간 보정 -> 달력 정규화 -> 사주 계산
- 사주 계산 -> 분석 엔진 -> 응답 변환

### golden
- 입춘 직전/직후
- 절기 경계 시각
- 자시 경계
- 한국 기준 대표 샘플
- 음력/윤달 샘플

### cross-check
- 메인 엔진 `lunar-python`
- 보조 엔진 `sxtwl`
- 둘의 차이가 나는 케이스는 수동 검토 목록으로 관리한다.

## 다시 검토해야 하는 조건
- `lunar-python`이 분 단위 계산 또는 특정 만세력 항목을 충분히 제공하지 못하는 경우
- 한국 기준 샘플 golden test에서 신뢰할 수 없는 불일치가 반복되는 경우
- 글로벌 확장 시 특정 국가/지역의 역사 시간 데이터 처리에 추가 계층이 필요한 경우
- 대운 계산 방식과 해석 규칙이 제품 요구와 더 세밀하게 결합되어야 하는 경우

## 이번 결정으로 확정된 개발 방향
- Python 백엔드 중심 유지
- 계산 코어는 `lunar-python`
- 시간 원천은 `zoneinfo` + `tzdata`
- 교차 검증은 `sxtwl`
- 분석 엔진과 LLM은 별도 계층 유지
- 메인 구현 전, adapter 인터페이스와 golden test 케이스부터 설계
