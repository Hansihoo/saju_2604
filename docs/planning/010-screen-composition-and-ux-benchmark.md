# Screen Composition And UX Benchmark 010

## 목적
- 사용자용 사주 서비스 화면을 다시 설계하기 전에 필요한 화면 요소를 먼저 정의한다.
- 실제 서비스와 공신력 있는 디자인 가이드를 참고해, 무엇을 보여주고 무엇을 숨길지 기준을 만든다.
- 다음 구현부터는 이 문서를 기준으로 정보 구조, 화면 우선순위, UX 규칙을 맞춘다.

## 현재 화면에서 보이는 문제
- 메인 화면에 개발자용 메시지가 섞여 있어 사용자 관점의 첫인상이 약하다.
- 한국어 타이포그래피에 맞지 않는 큰 제목 스타일 때문에 문장이 과하게 커지고 줄바꿈이 어색하다.
- 입력 영역과 결과 영역이 같은 우선순위로 보이면서 사용자가 “무엇을 먼저 해야 하는지” 즉시 이해하기 어렵다.
- 근거 데이터, 디버그 정보, 서비스 설명이 한 화면에서 경쟁해 핵심 흐름이 흐려진다.

## 조사에서 확인한 핵심 패턴

### 1. 긴 입력은 한 번에 다 보여주지 않는 편이 좋다
- GOV.UK는 질문형 서비스에서 “한 페이지에 한 질문” 접근을 기본으로 권장한다.
- Atlassian도 긴 form은 multi-step 또는 progressive disclosure로 부담을 줄이라고 안내한다.
- 우리 서비스도 출생일, 출생시각, 지역, 성별, 달력 구분을 한 화면에 모두 강하게 노출하기보다 단계적으로 보여주는 편이 맞다.

### 2. 사용자가 꼭 알아야 할 정보만 처음에 보여줘야 한다
- GOV.UK accordion 가이드는 모든 사용자가 봐야 하는 내용은 숨기지 말라고 권장한다.
- 따라서 사주 결과 화면에서 핵심 요약은 접지 않고 바로 보여주고, 오행/십성/대운/계산 근거는 펼쳐보기로 두는 것이 맞다.

### 3. 입력 오류는 페이지 상단 요약 + 필드 옆 메시지로 동시에 보여주는 것이 좋다
- GOV.UK validation/error-summary 패턴은 사용자가 제출한 값을 유지한 채, 상단 에러 요약과 각 필드 에러를 함께 제공하라고 안내한다.
- 우리 서비스도 “지역을 선택하세요”, “출생시각을 입력하세요”, “윤달 여부를 확인하세요” 같은 메시지를 상단 요약과 필드 바로 아래에 함께 보여주는 구조가 좋다.

### 4. 긴 옵션 목록은 일반 select보다 검색형 선택이 더 적합하다
- GOV.UK는 public-facing 서비스에서 긴 목록에 일반 select를 마지막 수단으로 보라고 안내한다.
- 지역 입력은 지금 기획대로 “입력 -> 추천 목록 -> 선택” 구조가 맞다.

### 5. 결과는 카드 나열보다 ‘요약 -> 근거 -> 확장’ 순서가 더 이해하기 쉽다
- GOV.UK summary list는 사용자가 입력한 값이나 핵심 사실을 요약해 보여줄 때 적합하다고 설명한다.
- 우리 서비스는 결과 화면 첫 블록을 “핵심 해석 + 입력 요약 + 시주 반영 여부”로 구성하고, 상세 카드는 그 아래로 내려야 한다.

## 벤치마크 정리

### The Pattern
- 공식 사이트는 `Customized, in-depth insights`와 `past, present and future`를 전면에 둔다.
- 해석 중심, 감정 중심, 관계 중심의 결과 경험이 강하다.
- 시사점:
  - 사용자 첫 화면은 “정확한 계산 엔진” 설명보다 “내 결과를 어떤 방식으로 읽을 수 있는지”를 먼저 보여주는 편이 좋다.
  - 결과 화면은 점수표보다 문장형 요약의 감정 밀도가 중요하다.

### Sanctuary
- 공식 사이트는 `live, on-demand personalized readings`, `daily horoscopes`, `birth chart readings`를 함께 강조한다.
- 서비스 신뢰를 “사람이 읽어준다”는 감각과 다양한 진입점으로 보완한다.
- 시사점:
  - 우리 서비스도 첫 화면에서 “이 서비스가 무엇을 주는지”를 한 문장으로 명확히 보여줘야 한다.
  - 차후 확장 시 “오늘의 흐름”, “추가 질문”, “궁합” 같은 재방문 포인트를 고려할 수 있다.

### Astro.com
- FAQ와 free chart 안내에서 정확한 출생시간, atlas, time zone, unknown time 처리 원칙을 강하게 드러낸다.
- 시사점:
  - 입력 화면에는 반드시 “왜 지역과 시간이 중요한지”를 짧게 설명해야 한다.
  - 출생시간 미상은 숨기지 말고 제한 규칙을 명시해야 한다.
  - 신뢰감은 화려한 그래픽보다 계산 기준 설명에서 나온다.

### Astro-Seek
- birth chart calculator는 birth date, time, place를 명확히 요구하고, free analysis를 함께 제시한다.
- 시사점:
  - 입력 화면의 CTA는 “계산 시작”보다 “내 사주 읽기”처럼 결과 지향 문구가 더 좋다.
  - 입력과 결과의 연결이 즉시 이해되도록 해야 한다.

## 우리 서비스에 필요한 화면

### 1. 사용자용 랜딩 / 시작 화면
- 목적:
  - 이 서비스가 무엇인지 설명
  - 바로 시작하도록 유도
  - 계산 신뢰 포인트를 짧게 제시
- 반드시 필요한 요소:
  - 서비스 이름
  - 한 줄 가치 제안
  - 시작 CTA
  - 신뢰 포인트 3개 이내
  - 언어 전환
- 추천 문구 방향:
  - “출생 정보로 사주를 계산하고, 핵심 해석부터 차분하게 보여드립니다.”

### 2. 입력 여정
- 목적:
  - 사용자가 정확한 입력을 부담 없이 완료하게 만들기
- 추천 구조:
  1. 달력 기준 + 생년월일
  2. 출생시각 + 시간 미상 여부
  3. 지역 + 성별
  4. 입력 확인
- 반드시 필요한 요소:
  - 단계 표시
  - 뒤로 가기
  - 짧은 힌트 문구
  - 에러 요약
  - 필드별 에러
  - 지역 자동완성
  - 시간 미상 안내
- 주의:
  - 한 화면에 너무 많은 설명을 넣지 않는다.
  - 힌트는 한 문장씩만 둔다.

### 3. 계산 중 화면
- 목적:
  - 사용자가 기다리는 동안 서비스가 실제로 계산 중임을 전달
- 필요한 요소:
  - 현재 단계 3개 정도
  - 너무 기술적이지 않은 메시지
  - 2~4초 이상 걸릴 때만 노출
- 추천 메시지:
  - “출생 시간을 보정하고 있습니다”
  - “사주 구조를 계산하고 있습니다”
  - “결과를 정리하고 있습니다”

### 4. 결과 요약 화면
- 목적:
  - 사용자가 가장 먼저 읽어야 할 해석을 깔끔하게 보여주기
- 반드시 필요한 요소:
  - 핵심 요약
  - 강점
  - 주의 포인트
  - 연애운
  - 직업운
  - 금전운
  - 행동 조언
  - 입력 요약 카드
  - 시주 반영 여부
- 추천 구조:
  - 상단: 핵심 한 문단
  - 중단: 3~4개 핵심 카드
  - 하단: 확장 가능한 근거 데이터

### 5. 근거 / 상세 화면 또는 상세 섹션
- 목적:
  - 계산 근거를 알고 싶은 사용자에게 설명 제공
- 필요한 요소:
  - 오행
  - 십성
  - 대운
  - 시주 제한 안내
  - 계산 기준 간단 설명
- 추천 방식:
  - 기본 접힘
  - 펼치면 설명이 나오는 details/accordion
- 주의:
  - 모든 근거를 처음부터 펼쳐두지 않는다.
  - 단, 모든 사용자가 꼭 알아야 할 제한 안내는 접지 않는다.

### 6. 오류 / 예외 화면
- 목적:
  - 입력 오류와 시스템 오류를 분리해서 처리
- 필요한 요소:
  - 다시 시도
  - 수정하러 가기
  - 현재 문제 설명
- 분리 기준:
  - 사용자가 고칠 수 있는 문제: 입력 에러
  - 사용자가 고칠 수 없는 문제: 계산 실패, 서버 오류

### 7. 개발자용 화면
- 목적:
  - pipeline status, debug trace, request echo 확인
- 정책:
  - 사용자 메인 경험과 반드시 분리
  - `/dev` 유지
  - 기본 진입은 사용자용 `/`

## 추천 IA

```text
/
  랜딩
  └─ 시작하기

/input
  1단계 달력/생년월일
  2단계 출생시각
  3단계 지역/성별
  4단계 입력 확인

/reading
  결과 요약
  └─ 근거 펼쳐보기

/error
  입력 오류 또는 시스템 오류

/dev
  개발자 검증 화면
```

## 화면별 구성 제안

### A. 랜딩
- 상단:
  - 로고
  - 언어 전환
  - 개발자 화면 링크는 숨기거나 작은 텍스트 링크로만 제공
- 본문:
  - 한 줄 핵심 메시지
  - 시작하기 버튼
  - 짧은 설명 2~3문장
- 하단:
  - 왜 시간이 중요한가
  - 왜 지역이 필요한가
  - 결과가 어떻게 보이는가

### B. 입력
- 좌측 정렬 단일 컬럼 우선
- 각 단계마다:
  - 질문 제목
  - 보조 설명 한 문장
  - 입력 컴포넌트
  - 에러 메시지
  - 다음 버튼
- 지역은:
  - 검색 입력
  - 바로 아래 추천 리스트
  - 선택 후 확정 카드

### C. 결과
- 1영역:
  - 핵심 요약
  - 현재 입력 기준 표시
- 2영역:
  - 강점 / 주의 포인트 / 연애 / 직업 / 금전 / 행동 조언
- 3영역:
  - 오행 / 십성 / 대운
- 4영역:
  - 계산 제한 및 안내

## 시각 디자인 방향

### 유지할 것
- 흰 바탕 중심
- 과한 장식 대신 정갈한 정보 구조
- 조용하고 신뢰감 있는 톤

### 버릴 것
- 한국어에서 지나치게 큰 세리프 제목
- 의미 없는 대형 hero 오브젝트
- 개발자용 정보가 메인 hero에 섞이는 구조
- 입력과 결과가 동시에 동일한 강도로 경쟁하는 레이아웃

### 추천 타이포그래피 방향
- 본문:
  - Noto Sans KR 계열처럼 안정적인 한글 sans
- 제목:
  - 한글 serif를 쓰더라도 짧은 제목에만 제한적으로 사용
  - 핵심은 크기보다 위계
- 규칙:
  - hero 제목은 2~3줄 안에서 끝나게
  - 한국어 제목 line-height는 너무 조이지 말 것
  - 긴 설명은 48~60자 폭 안에서 읽히게

## UX 규칙

### 입력 UX
- 달력 기준, 날짜, 시간, 지역은 필수 정보라는 점을 명확히 보여준다.
- 시간 미상은 허용하되 결과 제한을 즉시 설명한다.
- 사용자가 제출하기 전까지는 과한 검증을 하지 않는다.

### 결과 UX
- 첫 화면은 “요약”이 중심이다.
- 상세 근거는 사용자가 원할 때만 연다.
- 점수와 내부 등급은 사용자에게 직접 강하게 전면 노출하지 않는다.
- 계산 근거는 “왜 이런 결과가 나왔는지”를 설명하는 보조 장치로 사용한다.

### 신뢰 UX
- “정확한 계산 기반”과 “표현은 AI가 정리”라는 분리를 명시한다.
- 출생시간 미상, 윤달, 지역 선택 같은 민감 포인트에는 짧은 안내를 둔다.

## 구현 순서 제안

### 1차
- 사용자용 `/` 화면을 랜딩 + 시작 CTA 중심으로 재구성
- 개발자용 메시지를 메인에서 제거

### 2차
- 입력 화면을 step 방식으로 분리
- 지역 자동완성과 에러 UI 정리

### 3차
- 결과 화면을 요약 중심으로 재배치
- 오행/십성/대운은 접기 구조로 이동

### 4차
- 계산 중 화면, 오류 화면, 입력 확인 화면 추가

### 5차
- 모바일 최적화
- 접근성 점검
- 시각 디테일 정리

## 검증 기준

### 정보 구조 검증
- 사용자가 첫 3초 안에 “무엇을 하는 서비스인지” 이해하는가
- 사용자가 첫 10초 안에 “무엇을 먼저 눌러야 하는지” 이해하는가
- 사용자가 입력 중에 길을 잃지 않는가

### 입력 UX 검증
- 지역 선택을 실수 없이 완료할 수 있는가
- 시간 미상 정책을 이해하는가
- 에러 발생 시 어디를 고쳐야 하는지 즉시 알 수 있는가

### 결과 UX 검증
- 요약만 읽어도 결과를 이해할 수 있는가
- 근거를 보고 싶은 사용자는 쉽게 상세를 찾을 수 있는가
- 근거를 보고 싶지 않은 사용자는 화면이 복잡하다고 느끼지 않는가
