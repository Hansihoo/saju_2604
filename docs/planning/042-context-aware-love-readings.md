# 042. 연애 상황과 질문을 구분하는 풀이

작성일: 2026-10-07. 상태: 설계 완료, 런타임 미구현.

## 사용자 피드백과 확인한 문제

사용자는 연인이 없는 상태에서 연애운을 확인했지만 “서로에게 관심을 표현하고 각자의 시간을 존중하라”는 결과를 받았다. 이 결과는 새 만남에 관한 정보를 주지 않는다. 시기 미지원 안내를 덧붙여도 관계 성향 문장이 질문에 맞는 답이 되지는 않는다. 재미의 부족보다 먼저 질문·정보의 불일치를 해결해야 한다.

현재 `SajuPreviewRequest`와 `InterpretationPayload.profile`에는 연애 상황과 목표가 없다. `build_reading_plan.py`의 연애 규칙은 `love.spouse_house_ten_god` 한 feature로 기존 5개 십성 그룹 중 하나를 선택한다. 카탈로그의 `love.*`는 관계의 거리·표현·기대 등에 관한 프로젝트 해석이다. `love.meeting_window`는 여전히 `needs_rule_review`다. `DokkaebiReading`은 사용자의 상황을 묻지 않고 같은 `love` 카드를 표시한다. 기존 LLM의 문장이나 칩을 바꾸는 것만으로 이 결손을 해결할 수 없다.

인용된 결과의 개인별 명식·모델 원문·사실 참조는 이번 피드백에 제공되지 않았다. 특정 십성의 오류나 해당 사용자의 만남 시기를 이 문서에서 판정하지 않는다.

## 먼저 두 상황, 그 다음 원하는 답

| 사용자가 밝힌 상황 | 핵심 관심 | 필요한 정보 | 기존 설명의 위치 |
| --- | --- | --- | --- |
| 새 인연을 만나고 싶어 | 지금보다 만남의 기회가 눈에 띄는 기간은 언제인가? | 기준 기간, 원국과 대운·세운·절기 월운의 관계 단서, 적용 규칙·반대 단서·불확실성 | 연락·섭섭함·각자의 시간을 본문 대신 제공하지 않는다. 원국의 특징은 별도 보조 정보로만 둔다. |
| 지금 연애 중이야 | 관계가 진전되거나 조율이 필요한 시기는 언제인가? | 본인 명식의 기간 변화, 관계 진전/조율을 구별한 규칙과 검토 범위 | 현재의 관계 방식 해석은 선택해 읽는 보조 내용이다. 관계의 안정·갈등·결혼 시기를 입증하지 않는다. |

`썸`, 재회, 결혼 준비 등은 이번 기본 범위에 자동 추가하지 않는다. 이후 실제 원하는 답과 입력·규칙을 따로 정의한다. 사용자가 상황을 고르지 않으면 `unanswered`다. 솔로/커플을 사주·나이·성별로 추측하지 않는다. 연인이 있다는 사실만으로 결혼이나 상대의 속마음이 주 관심사라고 정하지 않는다.

## UX와 공개 조건

첫 화면은 기존 `운세 보기` 한 개 버튼과 제공 운세 안내를 유지한다. 연애 결과 안에서 “어떤 연애운이 궁금해?”와 두 상황을 보여주는 방향이다. 모든 이용자에게 첫 입력부터 연애 상태를 요구하지 않는다. 상황 선택 후에는 해당 상황에서 **실제로 지원하는 질문**만 표시한다. 지원하지 않는 시기 질문을 완성된 콘텐츠처럼 광고하지 않는다.

맥락 선택은 단순히 같은 문장 위에 라벨을 붙이는 기능이 아니다. 먼저 서버의 상황/질문별 지원 범위와 답이 있어야 한다. 새 인연 질문이 미지원이면 그 한계를 직접 알리고 연인이 있는 듯한 조언·장면·칩·풀이 메모·공유 문구를 붙이지 않는다. 이 차단은 잘못된 답을 없애는 단계이며 사용자 흥미나 만남 정보 제공의 완료가 아니다.

현재 단일 `love` 카드와 긴 풀이에는 상황별 지원 계약이 없다. 짧은 결과뿐 아니라 상세·다음 질문·공유에도 같은 맥락을 전달한다. 상황 변경이 새 고비용 모델 호출이나 전체 명식 재입력을 자동 유발하지 않도록 같은 계산 snapshot에 상황별 판정을 연결하는 방식을 우선 검토한다. 실제 API/캐시 계약은 구현 전에 기존 버전·개인정보·무상 검증 경로를 검토하고 확정한다.

## 내부 데이터와 책임

상황은 **사용자 제공 맥락**, 기간의 간지/십성/신살은 **계산 사실**, 그 조합의 뜻은 **해석 규칙**, 재미있는 표현은 **문구**다. 서로의 근거로 대신 사용하지 않는다.

```json
{
  "user_context": {
    "relationship_status": "single",
    "source": "explicit_user_selection"
  },
  "intent": "new_connection",
  "question_id": "love.meeting_window",
  "capability": {
    "status": "needs_rule_review",
    "missing": ["reviewed_relationship_timing_rules", "annual_and_monthly_interactions"]
  },
  "period_facts": [],
  "selected_rules": [],
  "answer": null
}
```

이는 제안 계약이다. 현재 API에 추가됐거나 질문이 지원된다는 뜻이 아니다. 빈 기간/규칙이면 answer를 만들지 않는다. 부족한 데이터를 기존 배우자궁 설명으로 채우지 않는다.

기간 사실에는 적용 시작/끝·기준 시간대·간지·등록된 십성·관련 위치와 상호작용·출생시간 미상 영향을 기록한다. 규칙에는 사용할 feature·해당 값/조건·제외 조건·출처·검토 상태·허용 claim을 둔다. 개인 내 기간 비교도 새 규칙이 필요하다. 기존 `love_impact` 휴리스틱이나 도화 개수를 그대로 만남 확률·유리한 날짜로 전환하지 않는다. 원국 신살의 개수·위치는 사실로 제시할 수 있지만 비교 표본 없는 “남들보다 많다”와 실제 연애 기회는 별개다.

기존 `question-reading-v1`의 answer/scene/tradeoff/action/analysis_note를 유지하되 질문에 맞는 규칙이 있는 경우에만 채운다. 문구·판정 규칙·사실 수집·맥락 계약 버전은 각각 관리한다. 상황별 새 규칙은 기존 관계 성향 규칙과 구별한다.

## 시기 질문의 직접 답 요구

2026-10-08 사용자는 “2024~2034년에 연인을 만난다고 예언하지 않으며 해마다의 관계는 별도 검토해야 한다”는 초안에 “그럼 왜 알려주는거야?”라고 지적했다. 원하는 결과는 **같은 사람의 여러 기간을 비교해 언제 만남 기회를 주목할지 설명하는 답**이다. 현재 대운의 재성 존재는 배경 사실로 남기며 그것만으로 이 요구를 충족했다고 판정하지 않는다. 한계를 반복하거나 일반 조언으로 본문을 길게 만드는 것도 해결이 아니다.

검토된 시기 기능의 답에는 다음 정보가 필요하다.

- 비교한 기간 범위와 실제 시작/끝, 표시 단위. 10년 대운을 만남 시점으로 그대로 대체하지 않는다.
- 다른 기간보다 주목한 이유를 구성하는 원국/대운/세운/월운 사실과 검토된 적용 규칙.
- 반대 단서, 미상 정보, 판정 동률/근거 부족 처리. 하나의 재성이나 도화 개수로 시기를 선택하지 않는다.
- 맥락에 맞는 행동과 계산된 판정을 구분한 문장. 행동이 실제 만남을 보장하지 않는다.

이는 구현 목표다. 현재 `love.meeting_window`의 `needs_rule_review`를 유지하며 기존 `favorable_periods`나 월운 일반 규칙을 만남 기회 상승일로 바꾸지 않는다. 수치 확률은 별도의 관측/보정 근거 없이는 제공하지 않는다. 조건부 명리 기간 비교도 규칙의 적용 범위와 전문 검토가 필요하다. 이름을 “흐름/기회”로 바꾸는 것은 그 검토를 대신하지 못한다. 미지원 사실은 메모에 숨기지 않는다.

## 결과를 재미있고 의미 있게 만드는 순서

1. 첫 문장은 사용자의 질문에 대한 새 정보를 준다. 주목할 기간과 판정이 실제로 준비되면 그것을 먼저 말한다. “서로 배려하세요”를 첫 답으로 삼지 않는다.
2. 이어서 같은 명식의 다른 기간과 어떻게 다른지, 무엇이 그 판정에 영향을 주는지 설명한다. 반대 단서가 있으면 확신을 낮춘다.
3. 행동은 맥락에 맞춘다. 새 만남에는 새로운 접점을 만들 행동, 교제 중에는 이미 있는 관계에서 조율할 행동을 다룬다. 행동이 사주에서 산출된 사건 예측인 듯 표현하지 않는다.
4. 본문의 일반적 배려 조언·안전 문구·칩 반복으로 분량을 채우지 않는다. 강한 표현과 캐릭터는 실제 정보의 의미를 전달하는 데 사용한다.
5. 전문 설명은 작은 기본 접힘의 `풀이 메모`에 계산 사실→선택 규칙→범위/예외 순서로 둔다. 핵심 지원 한계는 숨기지 않는다.

## 구현 순서와 완료 기준

| 단계 | 작업 | 통과 조건 | 현재 상태 |
| --- | --- | --- | --- |
| 1 | 원하는 답·맥락·지원 조건 정의 | 솔로/교제 중의 질문과 필요한 정보가 다르며, 미지원 대체 답이 금지됨 | Done: 이 문서와 제품 피드백 지식에 기록 |
| 2 | 기간 사실 및 만남/관계 변화 규칙 보강 | 원국/대운/세운/월운 자료, 출처·조건·예외·전문 검토, 시간 미상 처리 | Not started: 기존 만남 시기 기능은 미지원 |
| 3 | 상황별 서버 판정/응답과 검증 | 같은 snapshot에서 맥락에 맞는 질문/규칙/claim, 미지원은 명시적 보류 | Not started |
| 4 | 결과 내 상황 선택·상세·공유 연결 | 상황 미응답/변경/구형 응답/오류/키보드/모바일 확인; 자동 추가 모델 호출 없음 | Not started |
| 5 | 문구와 흥미 검토 | 다른 생일의 결과가 실제 관련 사실에서 달라지는지, 새 정보를 얻었는지 검토 | Not started: 재미·전문성 검증 완료로 기록하지 않음 |

검증 사례에는 솔로에게 “다음 데이트/연인에게 연락/서로 시간을 조율”을 유일한 답으로 주는 경우, 교제 중인 사람에게 새 상대 찾기를 권하는 경우, 미응답을 임의로 솔로로 처리하는 경우, 한계 안내 뒤 관계 성향 본문을 붙이는 경우, 맥락 변경 후 메모/공유/상세가 이전 맥락으로 남는 경우를 포함한다. 계산·해석·질문 적합성·사용자 흥미는 따로 평가한다. 자동/fixture 통과가 실제 흥미나 사건 예측 정확성의 검증은 아니다.

설계 회차의 검증: JSON과 기존 UI 정책 helper12 및 diff 검사가 통과했다. 기존 in-process fallback ASGI+실제 Vite 웹 shell verifier는456 PASS/3 WARN/기존 음력30일 FAIL이다. `.dev-runtime/reading-memo-20261007/love-context-design-asgi-user-story.json`에 보존했다. 새 상황별 runtime/역할 기준이 미구현이므로 이 결과를 새 맥락 기능의 통과로 해석하지 않는다. 새 모델 호출·서버 재시작·UI/계산/운영 설정 변경은 없었다.
