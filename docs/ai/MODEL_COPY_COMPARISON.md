# Model direction and Korean copy comparison

검토일: 2026-10-05. 버전: `model-copy-comparison-2026-10-05.1`.

후속 사용자 요청으로 비싼 모델을 제외한 **6 Luna / 5.6 Luna의 반복 앱 시험 및 5.6 Luna CLI 실제 생성**을 완료했다. 입력·경로·표본이 다른 후속 결과는 [저비용 Codex 시험](OPENAI_CHEAP_CODEX_TRIAL.md)에서 따로 읽는다. 아래 9개 CLI job의 실패 기록은 첫 시험의 관측 결과로 유지한다.

이번 한 사례에서는 Luna보다 현재 채팅 설정을 상속한 후보가 실행 가능한 콘텐츠 방향과 구체적인 캐릭터 문구를 더 잘 만들었다. Luna는 지원 한계와 계산 근거를 지켰지만 방향을 ‘필요한 자료 안내’에 머물게 했다. 가격만으로 서비스 전체를 Luna로 바꾸는 판단은 보류한다. 이는 모델의 일반 능력 순위나 실제 사용자 흥미를 입증한 결과가 아니다.

## 실제 실행 범위

| 후보/경로 | 실행 결과 | 해석 가능한 범위 |
| --- | --- | --- |
| GPT-6 Luna, 앱 에이전트 A | 생성 완료; 같은 맥락에서 세 과제 각 1개 | `spawn_agent`에 `gpt-6-luna` 지정. 서버의 정확한 snapshot과 청구 토큰은 미확인 |
| 현재 채팅 설정 상속, 앱 에이전트 B | 생성 완료; A와 같은 요약 사실·지침의 세 과제 각 1개 | 별도 모델 override 없음. 정확한 모델 ID가 노출되지 않아 ‘GPT-6.1 Sol 실행 성공’이라고 부르지 않음 |
| CLI의 GPT-6 Luna / GPT-6.1 Sol / GPT-5.4 | 모델별 세 과제, 총 9개 job 모두 계정·모델 호환 오류; 문구 생성 0 | 이 ChatGPT 로그인 방식에서 요청 모델이 지원되지 않는다는 오류. API나 앱 전체에서 이용 불가하다는 결론은 아님 |

앱 비교는 직접 공급자 API나 production prompt의 재현이 아니다. CLI는 reasoning `low`를 명시했으나 성공하지 않았다. 앱 에이전트는 reasoning override를 지정하지 않았다. 세 과제를 한 맥락에서 묶었으며 순서 효과를 통제한 독립 표본은 아니다. 호출 비용, 속도 분포, 재시도 비용은 측정하지 않았다. 운영 모델·키·provider·배포는 바꾸지 않았다.

## 입력과 세 과제

기존 backend에서 합성 S1/S2를 `as_of=2026-10-05T12:00:00+09:00`, fallback/`report_mode=none`으로 준비했다. 계산 정책은 기존 legacy 정책이다. 제공한 오늘 사실은 **일간 계, 일진 임자, 천간 십성 겁재, 연주 축과 오늘 지지 자의 합**이며 프로젝트 해석 범위는 자기 기준·역할 분담·협업과 연결이다. 이 해석은 전문가 검토나 실증 예측 검증을 완료한 규칙이 아니다.

1. **방향 결정:** 미래 인연·취업·직장 대우에 대한 관심을 주력 질문과 후보 두 개로 구성하고 필요한 근거 및 지금 제공할 수 있는 내용을 구별한다.
2. **방향 고정 문장화:** “오늘 같이 하는 일은 어디까지 맡는 게 좋을까?”에 답한다. 기억할 만한 한 문장, 가상 장면, 부담, 행동, 정확히 보존한 facts/한계, 동일한 공유 문장을 만든다.
3. **미지원 질문:** “연인은 언제쯤 만날 수 있을까?”에 지원 한계와 필요한 근거만 답한다. 성격/연애 타입, 가짜 시기/확률을 붙이지 않는다.

두 앱 후보에게 같은 요약 사실·제약을 전달했다. 저장한 `app-agent-input.json`은 준비된 source packet이며 실제 앱 호출 메시지의 byte 단위 복사본은 아니다. 실제 메시지는 공통 내용을 요약해 세 과제를 함께 전달했고 채팅 기록에 남아 있다. 향후 API 비교는 동일 prompt bytes·schema·reasoning 설정·동결 자료·표본 수를 고정해야 한다.

B의 단점도 남는다. 취업과 대우를 한 질문으로 묶어 서로 다른 질문/규칙의 소유권이 흐려질 수 있다. 작은 분석 노트는 A 96자/B 172자로 B가 길다. A의 “선을 그어야 일이 꼬이지 않아”는 행동 조언을 확정적인 결과처럼 읽게 할 여지가 있어 완화가 필요하다. 이는 편집상 위험 판단이며 실제 사건 예측 오류를 관측한 것은 아니다.

A의 “취업은 언제쯤 될 수 있을까?”도 원본 capability의 지원 시기에서 취업 성사 시기로 범위를 넓혔다. 새로운 기획 후보로 검토할 수 있지만 기존 지원 시기 기능에 그대로 연결하지 않는다.

## 코드 검사와 연결 계약

저장된 두 JSON을 기존 비교용 schema와 역할 제약으로 검사했다. 아래 수치는 흥미·의미·정확도 점수가 아니다.

| 검사 | Luna A | 현재 설정 상속 B |
| --- | --- | --- |
| JSON 구조/schema, 과제별 3종 | 모두 통과 | 모두 통과 |
| 오늘 facts 3개 및 원문 한계 2개 | 정확히 일치 | 정확히 일치 |
| 질문 고정·공유 문장 일치·가상 장면 표시·미지원 빈 역할 | 통과 | 통과 |
| 강조 답변 25–70자 | 47자, 통과 | 37자, 통과 |
| 강조 답변 한 문장 | 실패: 두 문장 | 통과 |
| 전체 기계 제약 20개 | 19 통과 / 1 실패 | 20 통과 |
| 원본 질문 ID 보존, 별도 연결 진단 | 실패: `love_meeting_window` 등 임의 변환 | 실패: `love_meeting`, `career_entry_reward` 등 임의 생성 |
| 원본 readiness 값 보존, 별도 연결 진단 | 통과 | 실패: 상태 문자열에 설명을 합침 |

질문 ID/readiness는 비교용 schema에서 단순 string이었다. 해당 진단을 엄격한 enum을 어긴 prompt 실패로 재해석하지 않는다. **현재 backend에 그대로 연결할 수 없다는 문제**다. 상위 모델도 문구가 좋다는 이유로 기계 계약을 맡겨서는 안 된다. 실제 연결에서는 backend가 ID·상태·facts·규칙·출처를 고정하고 모델은 허용된 문구 필드만 반환하게 하는 방향을 권고한다. 이번 턴에 production schema/routing을 구현한 것은 아니다.

문장 수는 구두점으로 검사했다. 자연어의 숨은 단정·미묘한 모욕·사실 범위 확대는 이런 검사만으로 증명하지 않는다.

별도 검토는 B가 미지원 답변의 `limitations`에 지원 한계를 추가한 점도 지적했다. 준비 packet의 원본은 `[]`였지만 실제 요약 앱 지침에 추가를 금지하는 조건이 별도로 강제됐다고 단정할 수 없다. 원문 보존을 요구하는 API 계약에 연결한다면 수정해야 하는 문제로 기록한다. 위 20항목 집계에는 이 추가 연결 진단이 포함되지 않는다.

## 별도 의미 검토

모델 이름을 숨긴 X/B, Y/A 입력을 별도 에이전트에 제공해 방향·문구·미지원 답변·근거·계약을 검토했다. 결과는 동일 증거 root의 `blind-review.json`에 보존한다. 이 검토는 입력에 대한 눈가림이며 도구 접근을 기술적으로 완전히 차단한 맹검이나 실제 소비자 연구는 아니다. 현재 채팅 설정을 상속한 검토 모델의 고유 문체 선호도 있을 수 있다.

검토자는 방향·오늘 문구에서 **X/B**를 선호했다. 현재 제공 가능한 별도 오늘 콘텐츠와 미래 질문의 관계, 발표 자료의 표를 대신 고치는 구체적 예시, 도깨비 보따리 비유를 이유로 들었다. Y/A는 원문/상태 보존과 짧은 분석 노트가 장점이며 한 문장·반말·과한 인과 표현은 단점으로 지적했다. X/B도 긴 분석 노트, 복합 질문, ID/상태 생성 문제를 지적했다.

첫 검토는 준비 packet에 원국·대운 요구가 보이지 않는다는 근거로 두 후보의 추가를 지적했다. 실제 공통 앱 메시지에는 원국·대운·세운·월운 검토 요구가 명시되어 있어 이 지적은 철회했다. 원문 결과와 `blind-review-correction.json`을 모두 보존하며 정정을 원문 위에 덮어쓰지 않았다. 검토자의 최초 미지원 선호 Y/A는 빈 한계 배열 보존을 우선한 판단이었다. 실제 앱의 추가 금지 조건을 단정하지 않도록 정정한 뒤에는 간결한 X/B 문구를 선호했다. 준비 packet과 실제 요약 메시지의 차이가 평가에 영향을 준 한계다. 후속 비교는 실제 호출 메시지 자체를 동결해 검토 입력으로 제공해야 한다.

## 모델 역할에 대한 권고

- **제품 방향과 편집 기준:** 사용자 피드백, 지원 범위, 질문/규칙/문구 역할을 사람이 검토 가능한 지식 문서로 먼저 고정한다. 필요할 때 상위 모델이 별도 개발/편집 작업으로 보강한다.
- **고객 요청의 문장화:** backend가 이미 선택한 질문·사실·해석 범위 안에서 저비용 모델을 비교한다. 이번 Luna 문구는 안전한 초안 후보지만 최종 표현 품질의 승자로 선정하지 않는다.
- **검증:** 사실·출처·지원 상태와 schema는 코드가 검사하고, 의미와 표현은 동결 사례의 별도 검토로 평가한다. 검증 실패 시 이미 검토한 fallback을 사용하도록 설계를 검토한다.

매 고객 요청마다 상위 모델로 기획한 뒤 Luna로 다시 쓰는 2회 호출을 제안하는 것은 아니다. 현재 고객 경로는 backend가 판단하고 모델이 문장화하는 구조다. 운영에서 역할/호출 구조를 바꾸려면 다사례 API 시험과 비용·실패 처리 검토가 먼저 필요하다.

다음 품질 비교에는 알려진/미상 출생시간, 복합 사실, 오늘·업무·연애의 지원 해석, 미지원 질문, KO/EN, 서로 다른 프롬프트/반복 표본을 포함해야 한다. API 키를 확인한 뒤 Solar/Gemini/DeepSeek 등 실제 공급자 출력과 token usage/latency/오류를 비교한다. 같은 한국어 문구가 같은 과금 토큰 수라는 가정을 검증된 비용으로 바꾸지 않는다.

## 증거와 미완료 범위

증거 root: `.dev-runtime/agent-verification-20261005/model-copy-comparison-20261005-1/`.

- `source-snapshots.json`, `*-input.json`, `*-schema.json`: 계산 snapshot 및 CLI 준비 입력. 실제 앱 요약 입력은 `app-agent-input.json`.
- `candidate-a.json`, `candidate-b.json`: 실제 앱 에이전트 최종 출력 원문.
- `check_app_outputs.py`, `app-validation.json`: 기계 검사와 source ID/상태 연결 진단, 출력 hash, 실제 실행 범위.
- `blind-review-input.json`, `blind-review.json`, `blind-review-correction.json`: 후보 이름을 숨긴 별도 의미 검토 및 입력 누락에 대한 정정. 원문 결과와 정정을 함께 읽는다.
- `compare.py`, `results.json`, `*-receipt.json`: 성공하지 않은 CLI 시험과 오류 기록. 앱 성공 결과와 혼동하지 않는다.
