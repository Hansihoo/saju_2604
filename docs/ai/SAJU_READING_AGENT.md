# Saju reading agent contract

이 문서는 계산·지식·해석·문구·UI를 수정하는 에이전트의 작업 규칙이다. 루트 `AGENTS.md`에서 연결한다. 먼저 `docs/PROJECT_STATUS.md`, `docs/CODEX_RUNBOOK.md`, `docs/planning/033-current-calculation-rules.md`를 읽는다.

## 1. 목표와 사실의 경계

제품의 약속은 **“사주에 있는 그대로 말해줄게.”**이다. 계산값을 충실하게 사용하는 것과 그 계산값으로 실제 사건을 정확히 예측하는 것은 별개다. 현재 카탈로그는 기존 프로젝트 해석을 정리한 `project_policy`이며 모든 출처의 `expert_review`는 `not_completed`다. 전문가가 검증한 명리 규칙이나 실증된 사건 예측으로 소개하지 않는다.

사용자에게는 질문에 바로 답하고, 구체적인 생활 장면과 행동을 제공한다. 내부에서는 각 문장이 계산 사실인지, 조건부 해석인지, 예시인지, 조언인지 구별한다. 문구가 재미있다는 이유로 적용 조건·범위·근거를 넓히지 않는다.

## 2. 처리 순서와 소유권

| 계층 | 입력 → 출력 | 수정 위치와 책임 |
| --- | --- | --- |
| 계산 | 생년월일·시간·성별·출생지 → 명식/보이는 오행/십성/대운 | 기존 계산 엔진. primary 정책을 유지한다. LLM이 재계산하지 않는다. |
| 사실 | 계산 결과 → `InterpretationPayload` | `build_interpretation_payload.py`. 시주 제외·계산 비활성·불확실성·실제 기간을 보존한다. |
| 지식 | 출처 + 적용 feature/value + 제외 조건 + 허용 범위 | `data/reading_knowledge/catalog.json`, `reading_knowledge.py`. 출처·규칙·문구 버전을 각각 기록한다. |
| 판정 | 사실 + 활성 규칙 → `ReadingPlan` | `build_reading_plan.py`. 미지원 조건에서 규칙을 선택하지 않는다. 충돌·미등록 제외 조건은 오류다. |
| 문장 | 선택된 질문/판정 → 4역할 문장 | 카탈로그 `wording.ko/en`. 모델은 같은 판정을 표현할 수 있지만 검증된 출처 표시를 만들 수 없다. |
| 표시 | 서버의 카드/역할 → 본문·강조 문장·분석 노트·공유 | React. UI는 계산이나 시점·확률·순위 판정을 새로 만들지 않는다. |

출생지는 출생 순간의 시간대·DST·지역 시각 보정에 사용한다. 현재 거주지는 받지 않는다. 오늘의 날짜 기준은 기존 period-flow 정책을 따른다.

## 3. 질문과 허용 답변을 먼저 정의한다

질문·진입·추천·문구 변경 전 [제품 피드백 지식](PRODUCT_CONTENT_KNOWLEDGE.md)과 JSON을 읽는다. QF-001~003은 이 프로젝트의 편집 기준이며 명리 사실/규칙과 별도다. 미래 질문에 성향 답변을 붙이는 대체를 허용하지 않는다.

2026-10-05 사용자 보정: 제품의 주력 관심사는 앞으로의 인연·취업·직장 변화와 시기다. 성격/연애 타입 질문을 첫 진입의 흥미 장치로 사용하지 않는다. 현재 가능한 성향 풀이로 미래 질문을 바꾸어 답하지 않고 필요한 기간 사실·해석 규칙·검토 요구를 먼저 보강한다. 계획은 [038](../planning/038-interest-led-reading-experience.md)을 따른다. 미지원 질문의 공개 제한과 아래 사실 경계는 유지한다.

| 질문 | 현재 가능한 답 | 아직 필요한 것 |
| --- | --- | --- |
| 나는 어떤 장점과 부담이 눈에 띌까? | 보이는 오행 분포에 관한 제한된 해석 | 종합 신강/신약·용신 판정을 오행 개수로 대체하지 않는다. |
| 나는 어떤 관계에서 편할까? | 배우자궁 십성 그룹의 관계 질문/예시/행동 | 실제 상대의 속마음·궁합·결혼 결과는 여기서 알 수 없다. |
| 어떤 업무 환경에서 덜 지칠까? | 월간 십성 그룹의 업무 방식 해석 | 실제 직장 상황·보상 조건·직무 적합성 정보는 별개다. |
| 언제 연인을 만날 가능성이 높아질까? | 미지원. 관계 패턴은 만남 시기의 답이 아니다. | 전문가 검토된 만남 시기 규칙과 원국·대운·세운·월운 상호작용. 실제 확률에는 관측 결과와 보정이 추가로 필요하다. |
| 언제 취업·인정·보상이 좋아질까? | 미지원. 업무 성향과 조언으로 시기 질문을 대신 답하지 않는다. | 취업/책임/평가/보상을 구별한 규칙과 시기 자료·사용자 목표. 책임 증가를 좋은 대우로 바꾸지 않는다. |
| 다른 사람보다 운이 얼마나 좋을까? | 비교를 보류한다. | 비교 모집단·산출 지표·표본 방식·기준 시점·검증. 합성 명식 분포를 실제 사람의 운 순위로 부르지 않는다. |

`QuestionCapability`에는 질문 ID, 상태, 지원 범위, 부족한 요구사항, 금지 claim을 기록한다. 현재 5개 질문은 `needs_rule_review` 또는 `needs_reference_population`이다. 버튼의 호기심을 채우기 위해 임의의 날짜나 백분위를 넣지 않는다. 아직 지원하지 않는 질문을 다음 질문으로 광고하지 않는다.

위 성향 질문은 기존 보조 결과의 지원 범위를 설명한 것이며 첫 진입/추천 후보가 아니다. 원하는 미래 질문을 기존 엔진이 답하기 쉬운 성향 질문으로 재작성하지 않는다. 독립 검증의 미지원 답변은 직접 한계와 필요한 요구만 설명하며 성향 본문·노트·다음 질문을 붙이지 않는다. 이런 한계 안내는 질문 만족을 달성한 답이 아니다.

## 4. 결과 형식: question-reading-v1

| 순서 | role / kind | 내용 | 금지 사례 |
| --- | --- | --- | --- |
| 0 | question | 사용자가 확인하고 싶은 질문 하나 | 질문 자체로 “내 몫만 늘어났다” 등 실제 경험이 있었음을 확정하지 않는다. |
| 1 | answer / interpretation | 선택된 규칙의 직접적인 해석 1문장. UI의 강조 문장 | 평균보다 뛰어남, 정확도 %, 이벤트 보장 |
| 2 | scene / illustration | “예를 들면”으로 시작하는 생활 장면 | 사용자의 실제 과거·성격을 관찰한 것처럼 표현 |
| 3 | tradeoff / interpretation | 장점과 함께 생길 수 있는 부담. 범위 제한이 필요하면 여기에 1회 | 장점을 모든 분야의 좋은 운으로 확대 |
| 4 | action / advice | 오늘 확인하거나 시도할 행동 하나 | 투자·합격·재회·승진을 보장하는 행동 |
| 5 | analysis note | 확인한 명식 사실 → 적용 해석 기준, 짧은 전문 문체 | 없는 사실 추가, 사용자 조언 반복, 전문가 검증을 암시하는 수사 |

카드 호환 필드의 매핑은 `title/subtitle = question`, `user_takeaway = answer`, `preview_paragraphs = [scene, tradeoff, action]`이다. `reading_structure.blocks`에는 네 역할 모두 들어간다. 각 block은 `rule_id`, `fact_ids`를 갖고 `facts`는 ID·값·실제 payload 경로를 갖는다. 이 링크는 **규칙의 적용 근거**이며 예시 장면이 실제로 일어났다는 증거가 아니다.

`reading_structure.analysis_note`는 같은 규칙의 `wording.ko/en.analysis_note`와 선택된 사실로 생성한다. 카드의 `basis_explanation`은 이 값과 같아야 하며 `basis_line`도 동일 facts로 구성한다. 성격 노트는 보이는 오행 분포와 최다 항목만 설명한다. 현재 대운 천간 십성을 쓰는 규칙의 노트에 다음 대운 비교를 섞지 않는다. 본문·노트 양쪽이 같은 잘못된 값으로 바뀌어도 실제 payload/카탈로그와 대조해 거부한다. 구조화된 성격 카드의 화면 제목과 공유 제목은 기존 hero가 아닌 동일 `question`을 사용한다.

사용자는 본문과 분석 노트를 항상 본다. 강조 문장은 약간 다른 서체, 본문은 고딕, 작은 캡션은 **분석 노트**로 유지한다. 구조 데이터나 출처 ID를 화면에 설명문으로 늘어놓지 않는다. 날짜와 계산 한계처럼 선택에 영향을 주는 정보만 표시한다.

문체는 친근한 도깨비 반말을 기본으로 하고 시비·모욕·공포 유발을 피한다. 분석 노트는 “월간 십성은 …입니다. 이를 근거로 … 해석 방향을 검토했습니다.”와 같은 정돈된 문장이다. 재미는 현실적인 질문과 상황에서 만든다. 사실성은 문체의 자신감으로 대신하지 않는다.

### 연결 예시

아래는 형식을 설명하는 합성 예시이며 특정 사용자의 결과가 아니다.

```json
{
  "question": "책임을 맡으면 인정도 따라올까?",
  "rule_id": "work_money.officer",
  "rule_version": 1,
  "source_id": "project-ten-god-policy",
  "provenance": "server_project_policy",
  "expert_review": "not_completed",
  "fact": {"id": "career.month_stem_ten_god", "value": "정관", "source_path": "career_facts.month_stem_ten_god"},
  "roles": ["answer", "scene", "tradeoff", "action"],
  "analysis_note": {
    "facts": ["월간 십성: 정관"],
    "reading": "월간 십성은 정관입니다. 이를 근거로 책임 범위와 평가 기준에 관한 해석 방향을 검토했습니다."
  }
}
```

이 규칙은 실제로 해당 십성 그룹이 공급된 경우에만 선택한다. “책임을 맡는 해석”에서 “다음 달 승진한다”로 이어지는 근거는 없다. 상세 풀이도 같은 answer/scene/tradeoff/action을 사용한다.

## 5. 현재 판정 조건과 실패 처리

- 계산 불확실성 `critical`이면 새 카탈로그의 모든 규칙 적용을 보류한다. 기존 결과와 경고는 유지하되 검증 marker를 붙이지 않는다.

- 연애·업무: 공급된 십성 라벨을 정규화하고 등록된 10개 라벨에만 매칭한다. 알 수 없는 라벨은 미분류다.
- 라이브러리의 `七杀/七殺/偏官`은 동일한 `편관`으로 정규화한다. 오늘/월간 규칙에서 알 수 없는 라벨을 비견 그룹으로 대신 분류하지 않는다. 원래 계산값과 정규화된 표시를 구별하고 KO/EN 회귀를 확인한다.
- 성격: 오행 5종의 비음수 개수와 실제 최다 항목이 `dominant_elements`와 일치해야 한다. 동률은 `core.mixed`. 보이는 오행은 전체 명식의 강약·길흉·용신이 아니다.
- 대운: 시간 미상, `luck_cycles/luck_flow` 비활성, disabled evidence, 현재 대운 없음, 실제 목록과 현재 대운 불일치, 해당 분석 행 없음에서는 지식 규칙을 선택하지 않는다. 실제 선택된 분석 행의 인덱스를 fact 경로에 기록한다.
- 미분류/제한 경우에는 기존 제한 안내를 보존하고 새 검증 marker를 붙이지 않는다. `reading_structure = null`은 문장의 의미가 검증되었다는 뜻이 아니다.
- 카탈로그 로더는 중복 ID, 없는 출처, 같은 조건에 중복 활성 규칙, 누락 언어, 잘못된 feature-topic 조합/제외 조건/치환 항목을 거부한다. 새 조건은 이름만 JSON에 적지 말고 코드 guard와 검증을 추가한다.
- 공급 사실이나 규칙·문구·역할·참조를 변조하면 새로 만든 plan과의 비교가 실패해야 한다. 서버 marker는 외부 모델 JSON을 파싱할 때 제외한다.
- 금지 문구 검사는 일부 확률·순위·보장형 취업/관계 표현을 잡는 보조 장치다. 모든 자연어 의미나 사실성을 증명하지 않는다. live 모델의 의미 검증은 여전히 별도 검토 대상이다.

## 6. 버전과 지식 변경 절차

1. 목표 질문과 현재 가능한 답을 정한다. 계산·규칙·문구·UI 중 무엇을 바꿀지 구별한다.
2. 출처를 읽고 원문 위치/해석 범위/학파 차이/예외를 기록한다. 현재 출처는 프로젝트 구현이며 문헌 인용이 아니다.
3. 적용 feature, 값, 제외 조건을 정의한다. 어떤 계산 사실이 필요한지 먼저 결정한다.
4. 규칙의 논리나 범위를 바꾸면 `rule.version`과 `knowledge_version`을 올린다. 문장만 바꾸면 `copy_version`을 올린다. 역할·필드 계약을 바꾸면 새 `format_version`과 호환 정책을 만든다. 프롬프트 변경도 별도 버전이다.
5. KO/EN 문장을 같은 판정으로 작성한다. 새 문구는 행동/예시를 별도 역할에 둔다.
6. 정상·반대 사실·경계·미상·누락·비활성·부정 입력·변조·언어·공급자 출처 주입을 확인한다. 타이밍/순위 기능에는 전문가 리뷰와 데이터 요구를 추가한다.
7. `docs/PROJECT_STATUS.md`, `docs/ai/WORK_LOG.md`를 갱신하고 미검증 범위를 남긴다. 기존 검증 FAIL을 성공 기준에서 빼지 않는다.

JSON 카탈로그는 현재 규모에서 코드 리뷰와 버전 관리가 쉬운 저장소다. DB/CMS/벡터 검색은 저자·문헌·규칙이 늘어난 뒤 선택한다. 검색한 문서를 곧바로 최종 판정에 쓰지 않고, 검토된 조건 규칙을 통해 연결한다. 편집 권한·승인 이력·버전 고정·배포 전 회귀가 필요해지면 동일 계약을 DB로 옮길 수 있다.

## 7. 검증과 현재 범위

역할별 Codex 검증 실행기는 `docs/ai/CODEX_AGENT_VERIFICATION.md`와 모듈 `app/tools/agent_verification/AGENTS.md`를 따른다. 계산 snapshot 이후 작업은 서버/계산 엔진을 import하지 않고 저장 artifact로 단독 실행한다. fixture 성공은 실제 모델 의미 검증이 아니며 검토 누락은 HOLD로 남긴다. production provider 설정과 fallback-only HTTP guard를 바꾸지 않는다.

```powershell
pnpm test:api
pnpm build:web
node scripts/verify-web-reading.cjs
pnpm verify:user-story
```

HTTP 검증 전 `GET /verification/provider`로 fallback을 확인한다. 검증 요청에는 `X-Saju-Verification-Provider: fallback`을 사용한다. 서버는 자동 reload하지 않으므로 변경 후 관리되는 프로세스를 재시작한다. 유료 LLM을 검증 목적으로 자동 호출하지 않는다.

구현된 범위는 메인 4주제의 21개 프로젝트 규칙, 5개 미지원 질문 상태, 서버 fallback의 문장/사실/분석 노트 추적, 프롬프트 계약, 동일 판정과 노트의 상세 4섹션이다. 독립 금전 상세 섹션, hero의 전체 문장 추적, 오늘/월간의 4역할 마이그레이션, 선택형 타이밍 상세의 기존 휴리스틱 해석은 이번 계약으로 전부 검증된 범위가 아니다. 실제 사용자 흥미·live 모델 문장의 의미·전문가 규칙 검토·실증 확률은 별도 검증이 필요하다.
