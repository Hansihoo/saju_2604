# DELIVERY_LOOP

## 목적
개발을 작은 반복 단위로 끊어 사용자와 계속 대화하면서 진행하기 위한 표준 루프다.

## 시작 전 전제
- 개발 회차를 시작하기 전에 기능 명세와 개발 전달 문서가 있어야 한다.
- 이번 회차 범위는 그 문서 안에서 가장 작은 구현 단위로 자른다.

## 기본 루프
1. 이번 회차 범위 합의
2. 코드 수정
3. build / test / lint / typecheck
4. 로그와 동작 확인
5. 문제 있으면 재수정
6. 간략 문서화
7. 다음 회차 제안

## 한 회차에 포함해야 할 것
- 이번 회차 목표
- 참조한 기능 명세 / 개발 전달 문서
- 변경 대상 파일 또는 영역
- 실행한 명령
- 검증 결과
- 발견된 문제
- 다음 회차 후보

## 회차 크기 기준
- 한 번에 하나의 작은 사용자 가치 또는 하나의 작은 기술 목표
- 여러 화면, 여러 API, 여러 정책 변경을 한 회차에 몰지 않는다
- 실패했을 때 되돌리기 쉬운 단위로 나눈다

## 검증 기본안
- 구현 후 `build`, `test`, `lint`, `typecheck` 중 관련 항목을 수행한다.
- UI/UX가 바뀌면 실제 화면 확인 또는 로그 확인을 남긴다.
- 실패한 명령이 있으면 무시하지 말고 원인과 다음 조치를 남긴다.

## 문서화 기본안
- 회차마다 긴 문서를 새로 쓰지 않는다.
- 바뀐 규칙, 명령, 결정만 짧게 반영한다.
- 구현보다 문서가 뒤처지지 않게 한다.

## 다음 회차로 넘길 때 남길 것
- 완료된 것
- 보류된 것
- 추가 질문
- 다음 회차 추천 시작점

## Codex에 말할 수 있는 예시
- `이번 회차는 로그인 화면 폼 검증만 구현하고 검증까지 진행하자`
- `이전 작업 다음 사이클을 진행하자. build, test, logs까지 확인해줘`
- `이 에러를 재현하고 수정 후 회귀 확인까지 이번 회차에서 처리하자`
- `이 기능 명세를 기준으로 첫 개발 회차를 시작하자`
