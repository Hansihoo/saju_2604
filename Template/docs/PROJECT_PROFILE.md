# PROJECT_PROFILE

## 부트스트랩 요약
- 프로젝트명: `suju-insight`
- 프로젝트 유형: 사주풀이를 제공하는 웹 서비스 템플릿
- 저장소 구조: 단일 repo
- 프런트엔드 기본안: React + Vite
- 백엔드 기본안: FastAPI
- 데이터베이스 기본안: PostgreSQL
- 프런트 배포 기본안: Vercel
- 백엔드 배포 기본안: Render
- CI 기본안: GitHub Actions
- 코드 스타일 강도: 중간
- 문서 언어: 한국어
- 자동화 목표: 가능한 범위까지 최대 자동화
- subagent 역할 후보: planner / implementer / verifier / documenter
- 작업 방식: 기획과 개발을 여러 회차로 나눠 사용자와 계속 대화하며 진행

## 현재 확정된 항목
- 실제 제품 코드는 만들지 않는다.
- 사주풀이를 제공하는 웹 서비스 방향으로 템플릿을 구체화한다.
- 템플릿 문서와 workflow 중심으로 저장소를 구성한다.
- 단일 repo 안에 문서, workflow, infra 자리까지 포함한다.
- 사람들의 일반적인 관습에 맞는 구조와 규칙을 우선 채택한다.
- 1인 개발 기준으로 과도한 프로세스보다 재현 가능하고 유지보수 가능한 기본값을 우선 채택한다.
- 기획은 단계별로 쪼개고, 개발은 작은 반복 루프로 진행한다.

## 미확정 시 작업 규칙
- 현재 작업에 필요한 값이 미확정이면 먼저 질문한다.
- 구현, 배포, 자동 수정은 관련 항목이 확정된 뒤에만 진행한다.
- 결정이 늦어질 수 있는 값은 `{{PLACEHOLDER}}`와 `TODO(USER):`로 남긴다.
- 질문은 꼭 필요한 것만 짧게 하고, 사용자가 모르면 권장 기본안으로 이어간다.
- 한 번의 인터뷰에서 모든 항목을 다 묻지 않고, 답변을 바탕으로 채울 수 있는 값부터 먼저 반영한다.
- 서비스 유형이 정해지면 그 유형에 맞는 다음 질문만 이어서 묻는다.

## 이번 부트스트랩에서 채운 기본값
- 프로젝트명: `suju-insight`
- 패키지 매니저: `pnpm`
- Python 패키지/실행 도구: `uv`
- 프런트 테스트 도구: `Vitest` + `Playwright`
- 백엔드 테스트 도구: `pytest`
- 린트/포맷 도구: `ESLint` + `Prettier` + `ruff`
- 타입 검사 방식: 프런트 `tsc`, 백엔드 `mypy`
- 로컬 실행 방식: 루트 표준 명령(`dev`, `test`, `lint`)을 기준으로 하되 앱별 명령을 병행
- 로그 수집 방식: 로컬은 앱 로그를 루트 명령으로 확인하고, 배포 후 로그는 Vercel/Render 로그로 확인
- 백엔드 배포 대상: `Render`
- Preview 환경 운영 여부: PR 단위 preview 사용
- Staging 환경 사용 여부: 초기에는 별도 staging 없이 운영
- 배포 승인 정책: 1인 개발 기준으로 production은 수동 승인 후 배포
- 문서 상세 수준: 중간. 결정, 명령, 검증 결과 중심으로 유지
- Git branch 전략 세부: `main` + 짧은 수명 feature branch
- commit 규칙 세부: `Conventional Commits`
- merge 방식: `squash merge`
- 자동 수정 허용 범위: 포맷터와 안전한 lint autofix까지만 허용
- 기획 회차 기록 위치: `docs/planning/*.md`
- 개발 회차 기록 위치: `docs/delivery/*.md`

## 회차 운영 기본안
- 기획 회차: 문제 정의 -> 사용 사례 -> 화면 구조 -> UX/UI -> 정책/범위 -> 개발 전달
- 개발 회차: 범위 합의 -> 구현 -> build/test -> 로그 확인 -> 수정 -> 짧은 문서화
- 각 회차 결과에는 `이번 회차 결정`, `남은 질문`, `다음 회차 시작점`이 포함된다.

## 초기 질문 기본안

2. 누가 사용하는가

5. 남은 항목은 다음 질문 묶음으로 넘긴다

- 백엔드 테스트: `pytest`
- 린트/포맷: `ESLint` + `Prettier` + `ruff`

## 커밋 메시지 규칙 기본안
- 형식: `[태그] 변경 내용`
- 태그 예시:
  - `[기획]` 요구사항, 사용자 흐름, 화면 구조 변경
  - `[개발]` 기능 구현, 로직 변경
  - `[수정]` 버그 수정, 회귀 대응
  - `[문서]` 문서 정리, 가이드 보강
  - `[배포]` CI/CD, 배포, 릴리즈 변경
  - `[구조]` 템플릿 구조, 폴더 구조, 공통 규칙 변경
- 기획 변경이 개발에 반영되면 제목에 그 사실이 드러나게 적는다.
  - 예: `[개발] 기획 변경 반영해 결과 조회 흐름 수정`
  - 예: `[문서] 기획 변경 반영해 기능 명세와 handoff 갱신`
