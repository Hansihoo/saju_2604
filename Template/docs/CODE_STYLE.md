# CODE_STYLE

## 기본 방향
- 스타일 강도는 `중간`을 기본으로 한다.
- 팀에서 널리 쓰는 관습을 우선 채택하되, 구조와 명령은 일관성을 더 중요하게 본다.
- 실제 프로젝트가 시작되면 프런트/백엔드 각각의 공식 권장 스타일을 우선 적용한다.
- 한 회차의 변경은 이해 가능하고 되돌리기 쉬운 크기를 유지한다.

## 권장 원칙
- 기능 단위로 코드를 모은다.
- 공용 모듈은 정말 반복이 확인된 뒤에만 추출한다.
- 설정, 환경변수, 외부 연동은 진입점을 한정한다.
- 로그, 예외 처리, 검증 규칙은 숨기지 말고 명시한다.
- 자동 포맷이 가능한 규칙은 도구에 맡기고, 구조 판단은 문서로 남긴다.

## 권장 아키텍처 기본안
- 프런트엔드: feature-based structure
- 백엔드: API layer / domain/service layer / persistence layer의 일반적인 layered structure
- 인프라/운영: 앱 코드와 분리된 문서/설정 디렉터리 유지

## 기본 금지사항
- 순환 의존 금지
- 무분별한 `common`, `utils`, `shared` 확장 금지
- 환경변수 직접 참조 분산 금지
- 비동기 에러 무시 금지
- 핵심 로직 변경 후 검증 생략 금지
- 템플릿 저장소에서 제품별 세부 규칙을 확정된 것처럼 박아 넣는 행위 금지

## 자동화와 자동 수정 가이드
- 포맷, import 정리, lint auto-fix는 우선 자동화 대상으로 본다.
- 구조 변경, 데이터 마이그레이션, 배포 설정 변경은 사용자 확인 전 자동 확정하지 않는다.
- 자동 수정 범위는 `docs/PROJECT_PROFILE.md`의 `{{AUTO_FIX_BOUNDARY}}` 확정 후 구체화한다.

## 회차별 완료 기준 기본안
- 이번 회차 목표가 한 문장으로 설명된다.
- 관련 검증 명령이 수행됐거나 미수행 사유가 있다.
- 로그 확인 또는 동작 확인 결과가 남아 있다.
- 다음 회차에서 이어갈 지점이 남아 있다.
