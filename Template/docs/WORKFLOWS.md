# WORKFLOWS

## 기획 workflow
1. 관련 `{{PLACEHOLDER}}`가 있으면 먼저 질문하고 확정 여부를 구분한다.
2. 이번 회차에서 다룰 기획 단계 하나만 정한다.
3. 사용자 문제와 사용 사례를 정리한다.
4. 목표와 비목표를 구분한다.
5. UX 시나리오와 실패 시나리오를 적는다.
6. 필요한 화면, API, 데이터 모델 후보를 적는다.
7. 미확정 항목을 질문지로 되돌린다.
8. 결과를 `PROJECT_PROFILE` 또는 별도 기획 문서에 반영한다.
9. 다음 기획 회차 질문을 남긴다.
10. 개발 가능 수준이 되면 기능 명세와 개발 전달 문서 초안을 만든다.

## 기능 개발 workflow
1. 현재 기능에 필요한 값이 미확정이면 먼저 질문한다.
2. 기능 명세와 개발 전달 문서가 준비됐는지 확인한다.
3. 이번 회차 구현 범위를 작은 단위로 좁힌다.
4. 요구사항이 문서로 확정됐는지 확인한다.
5. 작업 범위와 비범위를 적는다.
6. 구현 전 영향을 받는 명령과 검증 항목을 확인한다.
7. 코드 수정 후 build, test, lint, typecheck를 수행한다.
8. 로그와 동작 흐름을 확인한다.
9. 문제가 있으면 같은 회차에서 가능한 범위까지 재수정한다.
10. 문서와 명령 예시를 함께 갱신한다.
11. 다음 개발 회차 시작점을 남긴다.

## 버그 수정 workflow
1. 재현에 필요한 정보가 부족하면 먼저 질문한다.
2. 재현 조건을 먼저 적는다.
3. 기대 동작과 실제 동작을 분리한다.
4. 원인을 코드, 설정, 데이터, 환경 중 어디인지 좁힌다.
5. 수정 후 재현 케이스와 인접 회귀를 다시 확인한다.
6. 필요한 경우 운영 문서와 FAQ를 갱신한다.

## 유지보수 workflow
1. 현재 경고를 처리하는 데 필요한 정책값이 미확정이면 먼저 질문한다.
2. 의존성, 빌드, 테스트, 배포 경고를 수집한다.
3. 위험도와 영향 범위를 기준으로 우선순위를 정한다.
4. 자동 수정 가능한 항목과 수동 검토 항목을 구분한다.
5. 변경 후 표준 명령으로 회귀를 확인한다.
6. 변경 사유와 후속 TODO를 문서화한다.

## CI/CD workflow
1. 배포 대상, 승인 방식, 환경 구성이 미확정이면 먼저 질문한다.
2. PR 기준 필수 검증을 정의한다.
3. Preview 생성 여부와 조건을 확인한다.
4. main 반영 전 배포 영향 범위를 확인한다.
5. Production 배포 시 롤백 조건과 모니터링 포인트를 적는다.
6. 배포 후 로그, 헬스체크, 핵심 사용자 흐름을 다시 확인한다.

## 권장 운영 원칙
- 문서 없는 구현보다 문서 있는 느린 진행이 낫다.
- 자동화는 검증 가능한 단위부터 켠다.
- workflow는 프로젝트가 커질수록 더 짧고 반복 가능해야 한다.
- 한 번의 대화에서 전체 로드맵을 끝내기보다 다음 유효 단계가 명확한 상태를 더 중요하게 본다.
