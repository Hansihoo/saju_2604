# START_HERE

## 목적
이 저장소는 새 프로젝트를 빠르게 시작하기 위한 템플릿이다. 실제 제품 코드를 바로 작성하기 전에 프로젝트 프로필, 명령 체계, 문서, workflow, 검증 기준을 먼저 확정한다.

## 먼저 이해할 말
- `초기 설정`: 새 프로젝트에 맞게 이름, 기술, 배포, 문서 기본값을 정하는 단계
- `기획 회차`: 무엇을 만들지, 어떤 화면과 흐름이 필요한지 한 단계씩 정하는 대화
- `개발 회차`: 작은 범위를 구현하고 build/test/logs 확인까지 마치는 한 번의 작업 단위
- `내부 작업 모드(skill)`: Codex가 내부적으로 구분하는 작업 종류. 사용자는 몰라도 된다.

## 가장 쉬운 시작 방법
- 그냥 `프로젝트를 시작해보자`라고 말해도 된다.
- 그러면 Codex가 먼저 무엇을 만들지 물어보고, 답변만으로 채울 수 있는 값은 먼저 정리한다.
- 이후 현재 프로젝트 유형에 맞는 다음 질문만 순서대로 이어간다.

## 이 템플릿의 기본 가정
- 서비스 유형: 웹 서비스
- 저장소 형태: 단일 repo
- 기본 기술 후보: React + Vite, FastAPI, PostgreSQL
- 프런트 배포 후보: Vercel
- CI 기본 후보: GitHub Actions
- 자동화 목표: 가능한 범위까지 높은 자동화
- 문서 언어: 한국어 우선

## 먼저 할 일
1. `docs/PROJECT_PROFILE.md`를 열어 미확정 항목을 채운다.
2. `docs/QUESTIONNAIRE.md`로 도메인, 사용자, 운영, 배포 세부값을 확정한다.
3. `docs/PLANNING_STAGES.md`로 기획을 어떤 회차로 나눌지 정한다.
4. `docs/FEATURE_SPEC_TEMPLATE.md`와 `docs/IMPLEMENTATION_HANDOFF_TEMPLATE.md`로 기획 결과를 개발 입력 형식으로 정리한다.
5. `docs/COMMANDS.md` 기준으로 표준 명령 이름을 확정한다.
6. `docs/CI_CD.md`에서 환경, 배포 대상, 롤백 전략을 확정한다.
7. 실제 프로젝트가 정해진 뒤에만 구현용 디렉터리와 도구 설정을 추가한다.

## 작업 전제
- 현재 작업에 필요한 값이 `{{PLACEHOLDER}}` 상태라면 먼저 질문하고 합의한다.
- `template-bootstrap` 이전에 구현이나 배포 자동화부터 시작하지 않는다.
- 문서와 명령 체계가 먼저, 제품 코드는 나중이다.

## 지금 이 저장소에 없는 것
- 실제 서비스 기능 코드
- 프로젝트 고유 시크릿
- 확정되지 않은 배포 대상별 세부 설정
- 확정되지 않은 팀 규칙의 강제 설정

## 권장 부트스트랩 순서
1. Codex에게 `프로젝트를 시작해보자` 또는 `이 템플릿을 내 프로젝트에 맞게 초기 설정해줘`라고 말한다.
2. 기획 1단계만 정하고 싶으면 `이번 회차는 문제 정의만 하자`라고 말한다.
3. 다음 기획으로 이어가고 싶으면 `이전 기획 이어서 사용자 흐름과 화면 구조를 정리하자`라고 말한다.
4. 기획이 개발 가능한 수준이 되면 기능 명세와 개발 전달 문서를 먼저 만든다.
5. 구현이 확정되면 `이번 회차는 작은 범위만 개발하고 검증까지 하자`라고 말한다.
5. 운영 중 문제가 생기면 `이 문제를 재현하고 수정 후 다시 확인하자`라고 말한다.
6. 배포 전에는 `배포 전에 체크리스트부터 점검하자`라고 말한다.
7. 문서 차이가 생기면 `문서와 현재 상태를 맞춰줘`라고 말한다.

## skill 선택 가이드
- 프로젝트 기본값과 placeholder를 채우는 일은 `template-bootstrap`
- 요구사항과 사용자 흐름을 정리하는 일은 `product-planning`
- 승인된 범위를 구현하고 검증하는 일은 `feature-delivery`
- 운영 버그와 회귀를 다루는 일은 `maintenance-bugfix`
- 배포 검증과 롤백 계획을 점검하는 일은 `release-cicd`
- 이미 확정된 내용을 문서에 반영하는 일은 `docs-sync`

## 빠른 판단 기준
- 모르는 값은 비워두지 말고 `{{PLACEHOLDER}}` 또는 `TODO(USER):`로 기록한다.
- 실제 구현보다 템플릿 구조와 명령 체계를 먼저 고정한다.
- 자동화는 "실행 가능하고 검증 가능한 범위"까지만 켠다.
- 기획과 개발은 항상 "이번 회차 목표"를 먼저 좁히고 시작한다.
- 사용자는 내부 용어보다 자연스러운 말로 요청해도 된다.
- 질문은 현재 단계에서 꼭 필요한 것만 묻고, 프로젝트 유형에 따라 달라질 수 있다.
