# AGENTS.md

## 1. 이 저장소의 목적
- 이 저장소는 실제 제품 구현 저장소가 아니라, 새 프로젝트를 빠르게 시작하기 위한 프로젝트 템플릿 저장소다.
- 공통 명령, 문서 구조, workflow, skill 분리를 통해 기획/개발/유지보수/CI-CD를 반복 가능하게 만드는 것이 목표다.
- 모든 작업은 사용자와의 대화를 전제로 하며, 한 번에 끝내기보다 가장 작은 유효 단계로 나눠 진행한다.

## 2. 작업 시작 규칙
- 사용자가 `프로젝트를 시작해보자`처럼 자연스럽게 말하면, 먼저 만들고 싶은 것부터 파악하고 초기 설정 인터뷰를 시작한다.
- `docs/PROJECT_PROFILE.md`에 미확정 항목이 있으면 먼저 질문하고 합의한다.
- 현재 작업에 직접 영향을 주는 `{{PLACEHOLDER}}`가 남아 있으면 구현, 배포, 자동 수정 전에 먼저 질문한다.
- 실제 구현보다 먼저 기획, 구조, 명령, 환경, 배포 경계를 확정한다.
- 확정되지 않은 값은 추측하지 말고 `{{PLACEHOLDER}}`와 `TODO(USER):`로 남긴다.
- 기획과 개발은 한 번에 완결하려 하지 말고, 각 단계 종료 시 결과, 미결정 사항, 다음 질문을 남긴다.
- 질문은 꼭 필요한 것만 짧게 묻고, 사용자가 모르면 권장 기본안으로 바로 진행한다.
- 사용자에게는 `초기 설정`, `기획`, `개발 회차`처럼 쉬운 표현을 우선 사용하고, 내부 용어는 필요할 때만 덧붙인다.
- 한 번에 모든 항목을 다 묻지 말고, 현재 답변으로 채울 수 있는 값부터 먼저 채운 뒤 다음 질문으로 이어간다.
- 무엇을 만드는지에 따라 질문 항목을 바꾼다. 예를 들어 웹 서비스, API, 백오피스, SaaS, 멀티 서비스는 서로 다른 질문 흐름을 쓴다.

## 3. Skill 사용 규칙
- 새 프로젝트 부트스트랩은 `template-bootstrap`을 먼저 사용한다.
- 기능/요구사항 기획은 `product-planning`을 먼저 사용한다.
- 구현과 검증은 `feature-delivery`를 먼저 사용한다.
- 장애, 버그, 회귀 수정은 `maintenance-bugfix`를 먼저 사용한다.
- 배포 준비와 릴리즈 점검은 `release-cicd`를 먼저 사용한다.
- 문서 정리와 동기화는 `docs-sync`를 먼저 사용한다.

## 4. 표준 실행 순서
- 기획: 문제 정의 -> 사용자/사용 사례 -> 화면/UX/UI 방향 -> 실패 흐름 -> 범위 확정 -> 문서화 -> 다음 회차 질문
- 개발: 작업 범위 합의 -> 코드 수정 -> 빌드/테스트 -> 로그 확인 -> 필요 시 재수정 -> 간략 문서화 -> 다음 단계 합의
- 유지보수: 재현 -> 원인 분석 -> 수정 -> 회귀 확인 -> 문서화
- 릴리즈/CI: 검증 -> 배포 점검 -> 롤백/모니터링 계획

## 5. Definition of Done
- 변경 목적, 영향 범위, 실행 명령, 미확정 항목이 문서로 남아 있다.
- 관련 빌드/테스트/린트/로그 확인 절차가 수행되었거나 미수행 사유가 기록돼 있다.
- 남은 `{{PLACEHOLDER}}`와 `TODO(USER):`가 무엇인지 결과에 드러난다.
- 이번 회차에서 결정된 것, 미결정인 것, 다음 회차의 시작점이 분리돼 있다.
- 사용자 승인 없이 실제 서비스 구현 범위를 템플릿 범위로 확장하지 않는다.

## 6. 금지 규칙
- 템플릿 저장소에서 실제 서비스 로직을 만들지 않는다.
- 미정 값을 사실처럼 확정하지 않는다.
- 문서 없이 구조와 명령 체계를 먼저 생략하지 않는다.
- 검증 없이 CI/CD 자동화를 완료된 것처럼 표현하지 않는다.

## 7. subagent 사용 정책
- 큰 작업에서는 `planner`, `implementer`, `verifier`, `documenter` 역할을 명시적으로 분리할 수 있다.
- `planner`는 범위와 질문 정리, `implementer`는 코드/설정 변경, `verifier`는 build/test/logs 확인, `documenter`는 문서 동기화를 맡는다.
- 역할이 겹치지 않게 범위를 나누고, 결과는 문서와 명령 기준으로 다시 통합한다.
