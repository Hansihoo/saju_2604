# 목적
사용자 문제를 구현 가능한 요구사항으로 바꾸고, 개발 전에 문서와 범위를 정리한다.

## 시작 전 확인
- 해결하려는 사용자 문제나 아이디어가 있는가
- 이 작업이 구현보다 기획 정리가 우선인 상태인가
- 관련 프로젝트 프로필과 기존 문서를 확인했는가
- 이번 회차에서 다룰 기획 단계가 하나로 좁혀졌는가

## 암묵 호출 신호
- 무엇을 만들지, 어떤 화면이 필요한지, UX가 어떤 방향인지 대화로 정리해야 한다.
- 아직 구현보다 질문과 구조화가 더 중요하다.
- user story, acceptance criteria, 화면 흐름을 먼저 정리해야 한다.

## 수행 단계
1. 이번 회차 목표를 한 단계로 좁힌다.
2. 사용자와 목표를 정의한다.
3. 핵심 사용자 흐름과 실패 흐름을 정리한다.
4. 화면, API, 데이터 요구사항 후보를 구분한다.
5. 범위와 비범위를 분리한다.
6. 필요한 경우 user story와 acceptance criteria 초안을 만든다.
7. 위험, 가정, 미확정 항목을 정리한다.
8. 다음 기획 회차 질문까지 남긴다.

## 산출물
- 기능 기획 요약
- 사용자 시나리오
- 화면/UX 정리
- 실패/예외 케이스
- user story / acceptance criteria 초안
- 구현 전제와 TODO 목록

## 완료 조건
- 구현자가 바로 작업 범위를 이해할 수 있다.
- 모호한 요구사항이 질문 항목으로 분리돼 있다.
- 기획과 비기획 범위가 구분돼 있다.
- 다음 기획 회차를 어디서 다시 시작할지 알 수 있다.

## 금지사항
- 구현 세부를 기획 확정 없이 강행하지 않는다.
- 검증되지 않은 제품 결정을 사실처럼 적지 않는다.
- 실제 코드 작성으로 바로 넘어가지 않는다.
- 한 번에 전체 기획을 완성하려고 무리하게 확정하지 않는다.

## 사용자에게 다시 물어야 하는 경우
- 핵심 사용자 가치가 모호한 경우
- 실패 시나리오나 정책 결정이 필요한 경우
- 기능 우선순위가 충돌하는 경우
