# 목적
확정된 요구사항을 기준으로 구현, 검증, 문서 동기화까지 일관되게 진행한다.

## 시작 전 확인
- 요구사항과 비범위가 문서로 정리돼 있는가
- 영향을 받는 명령과 검증 절차를 알고 있는가
- 자동 수정 허용 범위가 확인됐는가
- 현재 기능 작업에 직접 영향을 주는 `{{PLACEHOLDER}}`가 남아 있지 않은가
- 이번 회차 구현 범위가 작은 단위로 잘려 있는가

## 암묵 호출 신호
- 이미 기획은 됐고, 이번 대화에서는 작은 범위만 구현하면 된다.
- 수정 후 build/test/logs 확인까지 같은 회차에서 보고 싶다.
- 문제가 생기면 바로 재수정하고 다음 회차 후보까지 남기고 싶다.

## 수행 단계
1. 이번 회차 구현 범위와 영향 범위를 확인한다.
2. 필요한 코드와 설정만 수정한다.
3. build, test, lint, typecheck를 수행한다.
4. 로그와 핵심 흐름을 확인한다.
5. 문제가 있으면 같은 회차에서 가능한 범위까지 수정한다.
6. 변경 사항을 문서와 명령 예시에 반영한다.
7. 남은 리스크와 다음 회차 후보를 기록한다.

## 산출물
- 구현 변경 사항
- 검증 결과
- 로그/동작 확인 결과
- 업데이트된 문서
- 남은 리스크 목록

## 완료 조건
- 관련 표준 명령이 성공했거나 실패 사유가 기록돼 있다.
- 기능과 문서가 서로 어긋나지 않는다.
- 사용자가 다음 단계 액션을 알 수 있다.

## 금지사항
- 미확정 요구사항을 임의로 확장 구현하지 않는다.
- 검증 없이 완료 처리하지 않는다.
- 문서 업데이트를 생략하지 않는다.
- 버그 재현과 원인 분석이 핵심인 작업에서 `maintenance-bugfix` 대신 쓰지 않는다.

## 사용자에게 다시 물어야 하는 경우
- 요구사항과 실제 코드 구조가 충돌하는 경우
- 자동 수정 범위를 넘는 큰 구조 변경이 필요한 경우
- 배포 영향이 큰 설정 변경이 포함되는 경우
